# ComicFlow 任务拆分与执行计划

**版本：** v1.0  
**状态：** 待确认  
**目标：** 在本地环境跑通 Automatic 模式的完整流程

**使用规则：**
- 每个任务开始前阅读 `DECISION_LOG.md` 和 `DATA_FLOW.md`
- 每个任务完成后执行 `ACCEPTANCE_PLAN.md` 中的验收步骤
- 任务之间严格按顺序执行，前置任务未验收通过不得开始下一个

---

## 总体目标

**核心目标：** 在本地环境验证从创建项目到导出视频的完整流程可用

**成功标准：**
1. 环境一键启动
2. Automatic 模式端到端无人工干预完成
3. 输出符合规格的 MP4 + 封面 + 字幕
4. 流程可重复执行，成功率 > 90%

**范围边界：**
- ✅ 做：验证现有流程、修复阻塞性 Bug、补充验收测试
- ❌ 不做：重构代码、优化性能、清理 guided 模式、新增功能

---

### 任务 0.2：验证基础环境

**目标：** 确保 Docker、数据库、API 可以正常启动

**前置条件：**
- 已安装 Docker Desktop
- 已安装 Python 3.12 + uv
- 已安装 Node.js + pnpm
- `.env` 文件已配置

**执行步骤：**
```bash
# 1. 启动全栈（含 postgres/redis/minio/api/worker/beat；迁移由 migrate 服务自动执行）
docker compose up -d

# 2. 验证容器状态
docker ps | grep comicflow

# 3. 验证健康检查（API 在宿主 18000，容器内 8000）
curl http://127.0.0.1:18000/health

# 4. 验证百炼 API
curl -X POST http://127.0.0.1:18000/api/provider-config/text/test
```

> ⚠️ 不要用 `uv run uvicorn ... --port 8000` 做验证——本机 8000 上的进程默认全 Mock
> Provider，会静默产出假资产。

**预期结果：**
- Docker 容器全部运行中（postgres, redis, minio）
- 数据库表结构创建成功
- API 健康检查返回 `{"status": "ok"}`
- 百炼 API 连接成功，返回 `{"ok": true, ...}`

**验收标准：**
参考 `ACCEPTANCE_PLAN.md` 阶段 0 验收清单

**如果失败：**
- 检查 Docker Desktop 是否运行
- 检查 `.env` 中的 `BAILIAN_API_KEY` 是否有效
- 检查端口 18000, 15432, 16379, 19000 是否被占用
- 查看 Docker 容器日志：`docker compose logs`

**预计耗时：** 30 分钟

**状态：** ⏳ 待执行

### 示例：任务 2.1 修复百炼 API 超时

**根因分析：**
- 现象：调用 `generate_story_text` 时返回 PROVIDER_TIMEOUT
- 根因：默认超时 30 秒，但百炼 API 响应需要 40-60 秒
- 影响范围：所有文本生成功能

**修复方案：**
```python
# 修改文件：backend/src/comicflow/providers/bailian_text.py

# 修改内容：
class BailianTextProvider:
    def __init__(self, api_key: str, base_url: str, timeout_seconds: float = 120):
        # 将默认超时从 30 秒改为 120 秒
        self._timeout = timeout_seconds
```

**验证方法：**
```bash
# 单元测试
uv run pytest backend/tests/test_bailian_text.py

# 手动验证
curl -X POST http://127.0.0.1:18000/api/projects/{id}/story
# 观察是否能在 120 秒内完成
```

**验收标准：**
- 文本生成不再超时
- 完整流程可以走通

## 风险与应对

### 风险 1：百炼 API 配额不足
**概率：** 中  
**影响：** 无法完成测试  
**应对：** 提前确认配额，必要时使用 Mock 模式验证流程

### 风险 2：发现大量 P0 问题
**概率：** 中  
**影响：** 超出预期工期  
**应对：** 优先修复最阻塞的问题，其他问题延后处理

### 风险 3：依赖服务不稳定
**概率：** 低  
**影响：** 测试结果不准确  
**应对：** 多次测试取平均值，区分偶发问题和系统性问题
