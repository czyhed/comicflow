## 2026-09-14：补充剧本与视觉资产阶段 Skill

### 背景

项目已有 `h3-prompt-writing`，但故事/剧本规划、角色资产锁定和场景空间锚点没有统一的阶段规则。用户要求接入 `XiaoLuo-AI-Drama-Skill` 与 `manju-laoli-skill`，并保留 H3 生成链路。

### 决策内容

1. 外部仓库只作为审查来源，固定 commit 保存在 `.scratch/external-skills/`；项目运行使用 `skills/manju-laoli-drama/` 和 `skills/xiaoluo-visual-assets/` 适配层。
2. Manju 规则用于故事、剧本、镜头连续性、对白语速和质量门禁；XiaoLuo 规则用于角色提示词、角色主参考图、三视图和场景背景图。
3. 每次 MiniMax H3 镜头继续执行现有 `h3-prompt-writing`，外部规则通过结构化字段和阶段 Prompt 传递，不直接替换 ComicFlow JSON 或 H3 协议。
4. Skill 文件、任务、文件列表和 SHA-256 写入执行元数据；不得写入 API Key、签名 URL 或供应商原始响应。

### 理由

三个 Skill 解决不同阶段的问题。保留现有 H3 适配器能维护已经验证的 `ref2va`、`i2va`、对白注入和尾帧级联契约；适配层避免将外部 Seedance、Markdown 或视角板格式误写入 ComicFlow 数据模型。

### 验收标准

- 离线聚焦回归 `70 passed`。
- Ruff、mypy 和两个项目 Skill 格式校验通过。
- 真实文本、图片和视频 API 调用数为 0。

3. **当前阶段目标**：

   - 使用百炼平台真实 API（文本、TTS、图像生成）

### 理由
- 技术栈已稳定运行，有完整测试覆盖，不应再变更
- Guided 模式增加复杂度但产品已不需要
- 先验证核心流程可用，再进行代码优化

### 影响范围
- 锁定所有依赖版本
- 后续任务不再考虑 guided 模式
- 所有新功能必须先通过端到端测试

### 验收标准
- 从创建到导出全流程无人工干预完成
- 输出符合规格的 MP4 + 封面 + 字幕
- 流程可重复执行，成功率 > 90%

## 2026-09-07：合成前置资产完整性门禁

### 背景
导出包"只有文字"的根因：`request_composition` 完全不校验资产覆盖率。10 镜头项目只生成 1 张画面也照样进入合成，FFmpeg 对缺画面的镜头用文字卡兜底，产出一部几乎全是文字的片子。故障在流水线尾部才显形，但根因在入口缺校验。

### 决策内容
1. `ProductionPipeline._composition_readiness()` 计算缺失清单，`request_composition` 在建 job 前门禁，不满足抛 `DomainError("ASSETS_INCOMPLETE", readiness)`。
2. **完整性口径**：每个镜头必须有 `valid` 画面；**仅当镜头有台词**（`dialogue` 或 `narration` 非空）才要求配音。无台词镜头按设计静音，不算缺失。
3. `DomainError` 增加可选 `detail`，由 API 错误响应体合并透出；`ASSETS_INCOMPLETE` → **409**。

### 理由
- 兜底不是容错，是把失败藏进交付物。合成的前置条件应当显式、在入口处拒绝。
- 拒绝必须自带缺失清单，否则前端只能再次遍历重算同一套规则，规则易分叉。
- 选 409 而非 400：这是资源状态未就绪（补齐资产即可重试），不是请求格式错误。

### 影响范围
- 部分生成的项目**不再能导出**——这是行为变更，此前"能导出"是缺陷表现。
- 4 个既有测试依赖此漏洞从半成品项目直达合成，已改为生成完整资产。
- 前端 `production-readiness.ts` 与本口径**必须保持一致**，改动需同步两侧。

### 验收标准
- 零资产项目请求合成 → 409 + 缺失镜头 ID 清单（已实测）
- 资产齐全 → 202 → `succeeded`（已实测）
- 回归：`backend/tests/test_composition_readiness.py` 6 个用例

## 2026-09-07：剧本契约按语义校验，不按字段存在性

### 背景
剧本拆分间歇性 502。根因：`normalize_preview` 要求 `dialogue` 和 `narration` **都**是 `str`；模型省略未使用的那个键时取到 `None`，`isinstance(None, str)` 为 False，整份合规剧本被判 `PROVIDER_INVALID_RESPONSE`。与生成时长无关，取决于模型当次是否省略可选键。

### 决策内容
1. 校验语义改为：`dialogue`/`narration` **至少一个**非空字符串；缺失键补 `""`。
2. 类型错误（非字符串）仍视为违约，继续拒绝。

### 理由
- "字段必须存在"和"镜头必须有台词"是两回事。契约要表达的是后者，代码实现的是前者，这是契约表述缺陷而非模型不合规。
- 宽进严出：可选键的缺省由服务端补齐，不把模型的合法自由度当错误。

### 影响范围
- 仅影响预览阶段校验，确认阶段提交预览原文，不重复调用 Provider。
- **同类缺陷未修完**：`normalize_preview` 仍要求场景五字段（`time`/`location`/`narrativeGoal`/`conflict`/`turningPoint`）全部非空，属同一类"按存在性校验"缺陷。本次只治了台词这一例，未治类——已登记为待办第四步。

### 验收标准
- 回归：`backend/tests/test_script_preview_lines.py` 4 个用例（缺键通过 / 双空拒绝 / 类型错误拒绝）

## 2026-09-07：前端就绪判断单一来源

### 背景
前端三处缺陷叠加，使用户能从几乎空的项目走到导出，且看不懂后端为何拒绝：`client.ts` 的 `request()` 丢弃错误响应体；就绪判断散落在各 workspace 各写一遍；`AudioWorkspace` 空状态没有生成入口，是死胡同。

### 决策内容
1. 新增 `ApiError` 类保留后端 `detail`，不再把结构化拒绝降级成裸错误码。
2. 新增 `frontend/src/production-readiness.ts` 作为就绪判断**唯一来源**，口径与后端 `_composition_readiness()` 对齐。
3. 新增 `use-batch-generation.ts`：逐镜头**串行**生成，`projectVersion` 必须**链式传递**（上一步返回的新版本喂给下一步）。
4. `VisualWorkspace` 删除写死的"一致性 96%"等**未经测量的造假指标**，改为展示真实图/视频资产。

### 理由
- 并行批量生成会因乐观锁版本冲突互相打掉，故选串行 + 版本链式传递。这是数据模型约束决定的，不是性能取舍。
- 就绪规则同时存在于前后端，只能靠"单一来源 + 明确标注需同步"约束，不能各处重算。
- 展示未测量的数字比不展示更有害——它让人以为质量已被验证。

### 影响范围
- 后端就绪口径变更时，`production-readiness.ts` 必须同步。
- 批量生成串行执行，10 镜头耗时线性增长（实测 6 镜头约 2 分钟）。

### 验收标准
- 已验：零资产 409 + 缺失清单渲染、6 镜头批量、MP4 1080×1920 H.264+AAC
- **未验**：浏览器实点 `use-batch-generation.ts`（仅用自写脚本验过等价流程，上线代码未跑）、`automatic` 模式、60 秒/10 镜头、E2E

## 2026-09-07：重复性验收暂定 1 次，先验正确性再谈稳定性

### 背景
`docs/ACCEPTANCE_PLAN.md` 阶段 1 要求"手动执行 3 次完整流程，成功率 100%"，阶段 3.1 要求 3 次中至少 2 次成功。3 次真实验收成本约 30 张 wanx 图。

同时存在一个更紧的问题：`use-batch-generation.ts` 是已提交的上线代码，但**一次没在浏览器里跑过**（上轮只用自写脚本验过等价的请求序列）。

### 决策内容
1. **先跑 1 次完整的 60 秒 / 10 镜头**（用户原始失败形状），约 10 张 wanx 图。
2. 这 1 次的目的是**验正确性**，不是验稳定性——不主张据此宣称"成功率 > 90%"。
3. 通过后再决定是否补到 2–3 次。补齐前，验收计划的"3 次"标准视为**未达成**。

### 理由
- 1 次跑不出成功率，但能暴露正确性缺陷（60 秒/10 镜头是已知的失败形状）。正确性没过，跑 3 次只是把同一个错误重复 3 遍。
- 成本节约是次要动机；主要动机是先用最贵的形状验最可能坏的那条路。

### 影响范围
- `ACCEPTANCE_PLAN.md` 的 3 次标准**暂未达成**，不得在任何总结里表述为已通过。
- 补到几次的决定推迟到第 1 次结果出来之后。

### 验收标准
- 60 秒 / 10 镜头、`automatic` 模式、**浏览器实点**走完全程
- 导出 MP4 抽帧确认为真实模型画面（非文字卡、非占位图）

## 2026-09-07：连通性测试只测连通性；Provider 错误映射收敛为单一来源

### 背景
准备验收时，`POST /api/provider-config/text/test` 对**完全健康**的环境返回 503 `PROVIDER_UNAVAILABLE`。容器内直连百炼两次均 HTTP 200，密钥和网络都正常——**是这个端点自己坏了**。

它是 `ACCEPTANCE_PLAN.md` 0.5 和 `TASK_PLAN.md` 0.2 的验收第一道门。它的失败方式会把人引向查密钥、查网络，即完全错误的方向。

两个缺陷叠加：

1. 端点用 `generate_script()` 探连通性，会走 `normalize_script_message()` 的**完整业务校验**（标题 2–80 字非空、场景数精确匹配时长档位、镜头数落在区间）。而提示词只说"返回最小 JSON"，模型照做返回 `{"title":"","scenes":[],"shots":[]}`——语法合法但内容空，必然违约。
2. 由此得到的 `PROVIDER_INVALID_RESPONSE` **不在**端点的内联映射表里，落到 `.get(..., "PROVIDER_UNAVAILABLE")` 兜底。同一张映射表在代码里有**三份副本且已漂移**：`pipeline.py` 的剧本生成路径同样缺这一项。

### 决策内容
1. 新增 `BailianTextProvider.check_connectivity()`：`max_tokens=1`、不带 `response_format`、**不做任何内容校验**；返回**实际应答的模型名**（模型被静默替换时可见）；401/403 单独归为 `PROVIDER_AUTH_FAILED`。
2. 新增 `providers/error_mapping.py` 的 `map_provider_error()` 作为**唯一映射表**，三处调用点全部改为调用它。
3. 映射表**同时收录两种拼写**（`PROVIDER_INVALID_RESPONSE` 与 `PROVIDER_RESPONSE_INVALID`）。统一命名另开，见待决策事项。
4. 端点响应去掉 `title` 字段（不再有剧本内容可返回），前端类型同步。

### 理由
- 端点叫 `test`，职责是"验证密钥+网络可用"。把剧本质量算作连通性失败，是**职责越界**，且越界的代价是谎报环境故障。
- 三份重复的映射表就是缺陷源本身。修掉个例而留下三份副本，下一个新增的 provider 错误码还会再漂一次——这是"治类不治例"。
- 拒绝返回 502（`PROVIDER_INVALID_RESPONSE`）而非 503：**有东西应答了**，说明 provider 可达，是响应形状问题，不是网络问题。

### 影响范围
- 端点响应体从 `{ok, title, model}` 变为 `{ok, model}`。唯一消费者是 `ModelApiSettings.tsx`，只用 `model`，不受影响。
- `pipeline.py` 剧本生成路径的错误码由此**修正**：契约违约此前被误报为 `PROVIDER_UNAVAILABLE`，现正确报 `PROVIDER_INVALID_RESPONSE`。
- 端点此前**零测试覆盖**，这是缺陷能存活的直接原因。现补三层测试（provider 探测 / 映射表 / 端点 HTTP 状态码）。

### 验收标准
- 回归：`test_text_provider_connectivity.py`（8 例）、`test_provider_error_mapping.py`（8 例）、`test_provider_config_endpoint.py`（6 例）
- **反向验证已执行**：分别重新注入两个缺陷，确认对应测试失败（含复现原始症状"健康 provider 得 503"），再恢复
- 真实栈实测：`200 {"ok":true,"model":"qwen-plus"}`（修复前 503）

## 待决策事项

### 统一 `PROVIDER_RESPONSE_INVALID` / `PROVIDER_INVALID_RESPONSE` 两种拼写？
**当前状态：** 待处理，已由 `map_provider_error()` 同时收录两者兜住
**背景：** `message_contract.py` 抛 `PROVIDER_INVALID_RESPONSE`，`bailian_text.py` 抛 `PROVIDER_RESPONSE_INVALID`，两个反向命名在代码里并存。这是上述 503 缺陷的**同源问题**：名字不一致导致映射静默落到兜底值。
**阻塞原因：** 重命名跨 provider / domain / api 三层及测试，不应与验收阻塞项捆在一起改。


### 重复性验收补到 2 次还是 3 次？
**当前状态：** 待第 1 次结果出来后决定（见上方 2026-09-07 决策）
**约束：** 在补齐之前，`ACCEPTANCE_PLAN.md` 的 3 次标准记为未达成。

### 资产清理机制何时做？
**当前状态：** 暂缓，优先级低于未验证代码
**背景：** 三处存储均无清理逻辑（`beat_schedule` 只有 outbox 轮询；`s3.py` 的 `expires_in` 是预签名 URL 有效期，与对象生命周期无关）。当前 MinIO 55M / 70 个对象，其中 exports 54 个对象对应的项目记录已被清库删除，成为**孤儿对象**。
**暂缓理由：** C 盘余量 127G，55M 无压力；`docker compose down -v` 已能整体复位（`comicflow-postgres` / `comicflow-objects` 两个卷）。清理机制的增量价值是"按项目精细复位"，属便利性，让位于验证未跑过的上线代码。
**触发条件：** 需要保留部分项目而只清理其余资产时，或磁盘占用变得可感知时。

### `normalize_preview` 场景字段校验是否一并放宽？
**当前状态：** 待处理（待办第四步）
**背景：** 台词校验已按语义修正，但场景五字段仍按存在性 + 非空校验，同类 502 风险仍在。
**阻塞原因：** 需先确认哪些场景字段是流水线真正的硬依赖，哪些可缺省。

### 是否清理 Guided 模式代码？
**当前状态：** 待讨论
**阻塞原因：** 需要先验证 automatic 流程完全可用
**预期决策时间：** 第一阶段验收通过后

### 是否重构 ProductionPipeline？
**当前状态：** 待讨论
**阻塞原因：** 1812 行单文件，职责过多
**预期决策时间：** 核心流程稳定后
