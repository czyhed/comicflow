## 1. 先理解各部分怎样配合

用户在浏览器里操作工作台，前端把操作提交给后端。后端检查输入和项目状态，把业务记录存到数据库；耗时的图片、视频和合成作业交给执行器。执行器调用远端模型或处理已有媒体，把文件放进对象存储，再更新数据库。页面读取新状态并展示结果。

| 部分 | 可以怎样理解 | 项目里具体负责什么 |
| --- | --- | --- |
| React前端 | 用户操作的工作台 | 编辑故事、镜头、角色，展示进度，播放候选，点击采用 |
| FastAPI后端 | 接收操作并检查规则的服务 | 验证请求，组织业务，读取或保存数据 |
| PostgreSQL | 项目的正式档案 | 保存故事、剧本、角色、作业、配置版本和素材引用 |
| Redis | 消息传递和临时状态存储 | 为Celery提供队列、结果后端，以及项目使用的临时状态 |
| Celery Worker | 后台执行器 | 接到消息后执行图片、视频、合成等作业 |
| Celery Beat | 定时调度器 | 定期要求Worker派发数据库里待处理的outbox事件 |
| MinIO | 媒体文件仓库 | 保存实际图片、视频、音频、封面、字幕 |
| 远端模型服务 | 生成内容的计算服务 | 根据输入生成文字、图片或视频 |
| FFmpeg | 程序化媒体加工工具 | 抽帧、检查音轨、裁剪、编码、合成 |

三类内容分开保存：项目记录在PostgreSQL，媒体字节在MinIO，队列消息在Redis。数据库中的图片引用与图片文件是两件事；文件存在但引用丢失，页面未必能找到；引用存在但文件不可读，页面也不能正常展示。

演示时可以说：

> “前端负责让人操作，后端负责检查和组织工作，数据库保存项目，执行器处理长任务，远端模型生成内容，对象存储保管文件。我们把这些能力组合成可持续编辑的创作流程。”

## 2. 前端技术：负责把数据变成可操作的页面

### 2.1 JavaScript、TypeScript与TSX

**是什么：** JavaScript是在浏览器里执行的程序语言。TypeScript在JavaScript基础上增加开发时的类型检查。TSX允许在TypeScript中描述React界面结构。

**项目中干什么：** 描述项目、镜头、角色、作业等数据的类型，编写按钮点击、保存、播放和错误处理逻辑。构建时转换成浏览器可以执行的JavaScript。

**具体例子：** 镜头时长应当是数字，图片作业用途只能是允许的选项。类型声明可以提前发现某个组件把错误类型的数据传给接口的问题。

**边界：** TypeScript不能保证模型输出正确，也不能替代后端校验。网络返回的JSON仍需要程序按实际结构处理。

**演示说法：** “TypeScript帮助开发阶段提前发现数据接错、参数传错的问题，提高维护时的可靠性。”

### 2.2 React与React DOM

**是什么：** React用于组织界面组件和状态；React DOM负责把这些组件显示到浏览器页面。

**项目中干什么：** 创建页、剧本编辑器、角色参考图、视频准备单等各有组件。数据变化后，React更新对应界面。`main.tsx`通过`createRoot`挂载整个应用。

**具体例子：** 选中一个镜头后，编辑区切换到该镜头；生成作业从执行中变成成功后，候选区域显示视频或图片。

**边界：** React不会生成图片或视频；界面状态更新也不代表数据库已经保存。保存必须经过后端接口并处理结果。

**演示说法：** “React让各个创作模块保持清晰，用户编辑和作业状态变化时，页面能够及时更新。”

### 2.3 TanStack Query

**是什么：** 管理从服务器读取的数据及其加载、缓存、错误和刷新状态的前端库。

**项目中干什么：** 获取当前项目快照，保存或采用后刷新相关数据，部分执行中的状态定时查询。项目ID参与查询键，避免把两个项目的数据混在同一份缓存里。

**具体例子：** 后端已保存一个新候选，页面刷新查询后显示它。`app/App.tsx`对符合条件的运行中项目状态设置1秒查询间隔；各媒体模块另有自己的作业查询逻辑。

**边界：** 页面缓存用于显示和减少重复读取，正式业务记录仍在数据库。查询重试不能被当成付费生成请求的自动重试策略。

**演示说法：** “它负责让页面显示的数据跟服务端保持同步，比如生成完成后刷新候选和项目状态。”

### 2.4 Zustand与localStorage

**是什么：** Zustand管理前端共享状态；localStorage是浏览器提供的本地保存空间。

**项目中干什么：** Zustand保存当前工作区、项目ID、选中镜头和导航变化。localStorage保存当前项目ID，重新打开页面时可以找回上次选择。

**具体例子：** 从分镜切到画面页时，页面知道用户正在处理哪个项目和哪个镜头。

**与TanStack Query的区别：** Zustand主要回答“用户选了什么”；TanStack Query主要回答“服务器目前保存了什么”。

**边界：** 清除浏览器存储会丢失本地选择，但不会因此删除数据库中的项目。localStorage也不是完整项目备份。

**演示说法：** “前端会记住当前操作位置，作品本身保存在后端，不依赖某一台电脑的浏览器缓存。”

### 2.5 React Router

**是什么：** 为单页应用提供浏览器路由和导航上下文的库。

**项目中干什么：** 入口已使用`BrowserRouter`。当前创建、剧本、角色等生产工作区主要由Zustand的`activeModule`选择组件，并非每个工作区都已经有独立URL路由。

**边界：** 有React Router依赖不等于已实现所有页面的深链接、刷新定位或复杂路由权限。

**演示说法：** “项目具备浏览器路由基础，当前核心操作按工作区组织。”

### 2.6 CSS、Tailwind CSS与Lucide React

**是什么：** CSS规定页面布局和外观；Tailwind提供工具类及构建支持；Lucide React提供可复用图标组件。

**项目中干什么：** CSS控制深色工作台、字号、按钮、编辑器、窄屏布局和状态提示；项目已接入Tailwind，但大量具体布局仍写在项目CSS中。Lucide用于工具按钮和导航图标。

**具体例子：** 主操作按钮、禁用按钮、失败提示、技术信息折叠区采用不同视觉状态，帮助用户识别当前能做什么。

**边界：** 这些技术改善可读性和操作体验，不决定模型生成质量。

**演示说法：** “界面把主要操作、状态和辅助信息区分开，减少用户在复杂制作流程中的查找负担。”

### 2.7 Vite

**是什么：** 前端开发服务器和构建工具。

**项目中干什么：** 开发时提供页面、热更新和API代理；发布时把源码构建成`frontend/dist`里的静态文件。生产环境由Nginx提供这些文件。

**具体例子：** 本地浏览器请求`/api`时，Vite根据`VITE_API_PROXY_TARGET`转发到后端18002；修改前端组件后开发服务器更新页面。

**边界：** Vite不承担后台生图、视频作业或正式数据库存储。生产运行无需继续用Vite开发服务器提供页面。

**演示说法：** “Vite提高开发和打包效率，正式上线后前端就是由Web服务器提供的静态程序。”

### 2.8 Node.js、pnpm与锁文件

**是什么：** Node.js运行前端工具和部分测试；pnpm管理JavaScript依赖；锁文件记录确定的依赖版本。

**项目中干什么：** 安装React等依赖，执行TypeScript检查、Vite打包和Node测试。前端Docker构建阶段使用Node与pnpm，运行阶段使用Nginx。

**边界：** 当前业务后端是Python/FastAPI，不因为构建使用Node就变成Node后端。`package.json`给出版本范围，`pnpm-lock.yaml`固定具体安装版本。

**演示说法：** “Node和pnpm主要支持前端构建，锁文件帮助不同机器安装相同版本。”

## 3. 后端技术：负责接口、规则和程序协调

### 3.1 Python

**是什么：** 后端业务使用的程序语言，项目要求Python 3.12及以上。

**项目中干什么：** 编写API、生产流水线、模型适配、数据库访问、后台作业及媒体处理协调逻辑。

**选择原因：** API、任务执行器和媒体工具可以共享代码，也便于连接模型服务生态。

**边界：** 使用Python不等于项目自己训练了模型。本项目业务服务器与仙宫云GPU服务属于不同运行环境。

**演示说法：** “Python承担业务编排和服务集成，实际模型推理由外部模型服务完成。”

### 3.2 FastAPI

**是什么：** 用Python编写HTTP接口的Web框架。

**项目中干什么：** 接收创建项目、保存剧本、生成图片、查询作业和采用视频等请求；关联请求schema、访问检查和业务方法；返回JSON或流式响应。

**具体例子：** 点击角色生成按钮后，图片作业接口接收项目、角色、用途、版本与操作ID，交给图片作业业务层创建记录。

**边界：** 接口能响应不代表Worker或远端模型就绪；长任务也不应都在一个普通HTTP请求里一直等待。

**演示说法：** “FastAPI把界面操作转换成受校验的业务请求，是前端与业务系统之间的入口。”

### 3.3 Uvicorn与ASGI

**是什么：** Uvicorn是运行FastAPI应用的服务程序；ASGI是Python异步Web服务器与应用之间的接口规范。

**项目中干什么：** 监听后端端口，把HTTP请求交给FastAPI，并支持异步请求和流式响应。容器中通过Uvicorn启动API。

**与FastAPI的区别：** FastAPI定义请求如何处理，Uvicorn负责让应用真正监听网络、收发请求。

**演示说法：** “FastAPI是接口应用，Uvicorn是把这个应用运行起来的服务进程。”

### 3.4 Pydantic与pydantic-settings

**是什么：** Pydantic描述和校验数据结构；pydantic-settings帮助应用读取和校验环境配置。

**项目中干什么：** 请求schema限制参数类型和允许值，例如图片用途、项目版本、任务号格式。模型输出还有专门的消息契约与业务校验，不完全靠Pydantic自动处理。

**具体例子：** `purpose`只允许`candidate`、`views`、`board`、`text-board`；非法值不能直接进入图片生成业务。

**依赖与实际用法：** 项目已声明pydantic-settings依赖，但当前运行入口主要通过`os.getenv`和`ProviderConfig.from_env`读取环境配置。不能把这个依赖的通用能力说成当前项目已经采用的全部配置实现。

**边界：** 字段类型正确不代表剧情好、台词准确或图片漂亮。创作质量还需要模型输出和人工判断。

**演示说法：** “数据先经过格式检查，再进入制作流程，避免错误参数一路传到模型和下游。”

### 3.5 asyncio与异步I/O

**是什么：** Python的异步任务机制；I/O指网络请求、数据库或文件等输入输出操作。

**项目中干什么：** 网络等待期间让程序能够继续处理其他异步工作，协调文本流式事件、数据库请求及供应商查询。部分阻塞媒体处理通过线程执行。

**边界：** 异步机制改善服务协调，不会直接加快远端GPU生成。同样，API中的`asyncio`任务不是Celery持久作业，API进程崩溃后的恢复能力不同。

**演示说法：** “后端尽量在等待网络时继续处理其他工作，但模型本身的计算速度由远端服务决定。”

### 3.6 HTTPX与python-multipart

**是什么：** HTTPX是Python HTTP客户端，用来向其他服务发请求；python-multipart支持FastAPI处理multipart表单和文件请求。

**项目中干什么：** HTTPX向文本、图片、视频服务提交内容，查询任务、上传素材和下载结果。multipart把参数与图片文件放在同一个HTTP请求中；仙宫云上传由HTTPX客户端构造，不是由python-multipart负责发送。

**具体例子：** H3适配器带鉴权向`/api/v1/jobs`提交文字字段与参考图片字节，然后查询返回的任务号。

**边界：** 客户端连通不等于模型可用；超时也不能简单理解为供应商没有收到请求。

**演示说法：** “网络层负责把我们准备的文字和图片按供应商协议送过去，再查询和保存结果。”

### 3.7 uv、虚拟环境与uv.lock

**是什么：** uv是Python依赖和环境工具；虚拟环境隔离项目依赖；`uv.lock`记录锁定版本。

**项目中干什么：** 在开发、检查和Docker构建时安装确定版本的Python依赖，创建项目使用的`.venv`，运行工具和服务。

**边界：** uv不是业务框架，也不执行模型推理。锁文件能固定软件依赖，不能固定远端模型随机输出。

**演示说法：** “依赖版本锁定让开发、检查和部署使用更一致的软件环境。”

## 4. 数据库技术：负责保存业务事实

### 4.1 PostgreSQL

**是什么：** 支持事务、约束和查询的关系数据库。

**项目中干什么：** 保存项目、角色、模型配置版本、图片和视频作业、outbox事件。当前大量故事、镜头和资产引用保存在项目的JSON payload中，不是所有对象都有独立关系表。

**具体例子：** 用户关掉浏览器后，图片作业的状态和供应商任务号仍在数据库里。再次打开页面可以读取，不必只凭前端记忆判断。

**关键作用：** 事务让相关写入一起成功或一起回滚；唯一约束等机制协助阻止重复操作和冲突。

**演示说法：** “数据库保存的是创作过程的正式记录，包括版本、生成状态和结果引用。”

### 4.2 SQLAlchemy、ORM、Repository与asyncpg

**是什么：** SQLAlchemy帮助Python读写数据库和管理事务；ORM把数据库行映射为Python对象；Repository是项目自己的数据访问模块；asyncpg是连接PostgreSQL的异步驱动。

**项目中干什么：** 业务层通过Repository读取项目和角色，由SQLAlchemy组织查询、事务和更新，再通过asyncpg与PostgreSQL通信。

**具体例子：** 图片作业领取时需要检查是否可执行，并原子地取得租约；仓储层处理数据库条件更新，业务层接着准备图片输入。

**关系：** PostgreSQL是数据库，SQLAlchemy是访问工具，asyncpg是连接驱动，Repository是本项目组织访问职责的代码。

**边界：** ORM不自动解决所有并发问题；仍需要版本检查、约束、条件更新和测试。

**演示说法：** “业务代码通过统一的数据访问模块读写数据库，保存和并发规则在这一层明确执行。”

### 4.3 Alembic

**是什么：** 管理数据库表结构版本的工具。

**项目中干什么：** 当增加图片作业等结构时，用迁移文件描述表结构变化，并记录当前数据库到了哪个版本。

**与普通保存的区别：** 保存剧本更新某个项目内容；Alembic更新数据库结构。代码更新与结构升级是两个操作。

**边界：** Alembic不会自动把本机全部项目、MinIO文件和加密主密钥搬到服务器。普通发布也不能随意执行结构迁移。

**演示说法：** “数据库升级有版本记录，避免新代码需要的结构与服务器实际结构不一致。”

### 4.4 SQLite与aiosqlite

**是什么：** SQLite是轻量文件数据库，aiosqlite提供异步访问支持。

**项目中干什么：** 支持部分本地持久化测试。正式运行的业务事实使用PostgreSQL。

**边界：** SQLite测试通过不能单独证明PostgreSQL的并发、事务和约束行为；因此还需要真实隔离数据栈测试。

**演示说法：** “轻量数据库帮助快速测试，正式数据库行为另外用真实PostgreSQL验证。”

## 5. 后台执行：负责长任务、防重和恢复

### 5.1 Celery

**是什么：** Python后台任务框架，包含任务定义、发送、执行和结果管理。

**项目中干什么：** 把耗时操作交给独立Worker，例如执行持久图片作业、视频作业、自动生产推进与合成作业。文本故事和拆分的当前流式入口可以直接由API处理，不能把所有操作都概括为Celery作业。

**演示说法：** “媒体生成在独立进程中执行，浏览器负责查看进度，项目状态保存在数据库里。”

### 5.2 Celery Worker

**是什么：** 持续接收并执行Celery任务的进程。

**项目中干什么：** 从队列取得作业ID，读取固定配置和输入，领取租约，调用供应商或FFmpeg，并保存进度和资产。

**具体例子：** 本次角色图片卡住时，API已保存作业，Worker却停止。恢复后，同一个作业成功生成，调用次数为1。

**边界：** Worker运行也不等于所有供应商健康。当前本地Worker为solo、concurrency=1，长任务可能占住执行器并延迟后续消息。

**演示说法：** “Worker是实际执行后台工作的进程。页面能打开而Worker未运行时，长任务仍会等待。”

### 5.3 Redis、Broker与结果后端

**是什么：** Redis是内存数据存储，也可按配置持久化。Broker是传递任务消息的角色；结果后端保存Celery任务执行结果。

**项目中干什么：** Redis支持Celery队列和结果，以及锁、事件和临时状态。命名空间前缀区分本应用队列与其他应用或验证环境。

**与PostgreSQL的区别：** Redis承担消息和临时协调，PostgreSQL保存正式项目与媒体作业记录。页面不能只靠队列是否有消息判断作业是否成功。

**边界：** 命名空间隔离不是独立Redis服务器，也不等于已经建立Redis ACL权限隔离。

**演示说法：** “Redis把任务消息送给执行器，数据库保存任务真正进行到了哪一步。”

### 5.4 Celery Beat

**是什么：** 按时间表发送任务的调度进程。

**项目中干什么：** 当前每2秒发送一次outbox派发任务，由Worker查数据库中的pending事件并发布到队列。

**与Worker的区别：** Beat负责到时间发消息，Worker负责执行。Beat本身不会直接生成图片或视频。

**边界：** Worker停止时，Beat发出的消息仍可能等待；Beat停止时，数据库新写的outbox可能无人派发。

**演示说法：** “定时调度器定期检查需要派发的工作，执行器再实际处理。”

### 5.5 Transactional Outbox

**是什么：** 一种可靠派发方式，不是额外模型或新服务器。业务记录和待发送事件在同一数据库事务中写入，随后由派发器把事件发布到消息队列。

**项目中干什么：** 避免图片或视频作业已经写入数据库，但任务消息因服务中断没有送出的情况。发送被Broker接受后再把事件标记为published。

**具体例子：** 图片作业与`production.image.queued`事件一起保存。之后派发器把事件转换为`run_image_job`消息。

**边界：** Outbox不能保证供应商跨网络绝对只扣费一次。消息可能重复投递，执行阶段还要检查作业状态。

**演示说法：** “先留下可靠的待处理记录，再派发执行，服务中断后仍知道哪些工作没有发出去。”

### 5.6 操作ID、版本、指纹、租约与检查点

这些是业务可靠性机制，不是五个外部服务。

| 机制 | 作用 | 项目里的例子 |
| --- | --- | --- |
| operationId | 识别同一次用户生成操作 | 同一操作重复提交时查已有作业，避免另建一个 |
| expectedVersion | 判断用户提交时项目是否已变化 | 旧编辑页提交不能静默覆盖新保存内容 |
| 配置revision | 记录作业选用哪版模型配置 | 作业执行时按记录版本读取，不任意改用最新模型 |
| 输入指纹 | 检查准备单与实际生成输入是否一致 | 角色图或镜头修改后要求重新核对准备单 |
| 租约 | 限制同一作业同时由多个执行者处理 | 数据库条件更新领取，过期后按状态判断恢复 |
| 检查点 | 保存已经做完的阶段 | 已有供应商任务号就继续查询，已有文件就继续保存 |
| unknown状态 | 标记已开始提交但结果不确定 | 不自动重发付费请求，先核对供应商 |

消息“送到一次”与业务“只执行安全的一步”不是同一个保证。网络超时后上游可能已经接受请求，所以不能统一把失败处理成再生成一次。

**演示说法：** “系统区分排队、提交、查询、保存等阶段。失败后按已有记录恢复，减少重复提交和重复生成的风险。”

## 6. 文件、媒体与凭据处理

### 6.1 MinIO、S3与boto3

**是什么：** MinIO是对象存储服务；S3是广泛使用的对象存储接口体系；boto3是项目使用的Python访问客户端。

**项目中干什么：** 上传和读取生成图片、视频、音频及导出包。数据库保存`objectKey`、媒体类型等引用，不把大视频直接塞进项目JSON。

**具体例子：** 模型完成的视频下载到应用后写入对象存储。以后播放或合成读取这份已保存的视频，不要求GPU实例继续运行。

**边界：** MinIO不是生图工具，也不是模型任务队列。完整迁移要同时处理数据库引用和媒体文件。

**演示说法：** “模型负责生成，我们把结果存进自己的媒体仓库，后续播放和合成复用保存的素材。”

### 6.2 签名URL

**是什么：** 含有限期访问授权的文件地址，由服务端按对象存储规则生成。

**项目中干什么：** 让前端在允许时间内读取媒体，不把对象存储长期密钥交给浏览器。

**具体例子：** 数据库保存稳定的objectKey，展示时生成可用访问地址。地址过期应根据引用重新取地址，不能据此认定图片已经丢失。

**边界：** 获得地址的人在有效期内通常能访问它；签名URL不能替代项目访问控制。

**演示说法：** “素材引用长期保存，页面访问时拿到有时效的文件地址。”

### 6.3 Pillow

**是什么：** Python图片读取和处理库。

**项目中干什么：** 检查图片能否解码、尺寸和格式，以及现有参考板等图片处理流程。

**具体例子：** 本次恢复的角色图片从存储读取后，用Pillow验证内容，得到1536×1024尺寸。

**边界：** Pillow处理已有像素，不是远端生图模型，验证能打开也不代表人物身份或多视角质量正确。

**演示说法：** “生成结果保存前后可以检查图片文件本身，人物质量另外由用户确认。”

### 6.4 FFmpeg与ffprobe

**是什么：** FFmpeg执行媒体转码、裁剪、拼接和抽帧；ffprobe读取媒体的时长、编码、分辨率和音轨等信息。

**项目中干什么：** 核查有效视频，提取尾帧或封面，归一媒体规格，复用原声，按镜头顺序合成导出。

**具体例子：** 多个采用镜头规格不同，先归一到当前竖屏合成规格，再拼接成MP4；有台词却缺音轨时不能直接当作声音完成。

**边界：** 转成1080×1920只改变输出规格，不能把低分辨率源素材自动变成原生高细节视频。FFmpeg不需要再调用视频模型。

**演示说法：** “生成模型出素材，FFmpeg负责把已有素材加工成可以播放和交付的文件。”

### 6.5 MP4、H.264、AAC、JPEG与SRT

| 名称 | 是什么 | 当前用途 |
| --- | --- | --- |
| MP4 | 装视频、音频等数据的容器格式 | 交付`video.mp4` |
| H.264 | 视频编码方式 | 当前合成视频编码 |
| AAC | 音频编码方式 | 当前合成音轨编码 |
| JPEG | 常见图片格式 | 交付`cover.jpg` |
| SRT | 带时间段的文本字幕格式 | 交付`subtitles.srt`草稿 |
| 30fps | 每秒30帧的播放规格 | 当前视频合成输出帧率 |

MP4与H.264不是同一层概念；字幕文件交付不等于字幕已烧录进视频。当前SRT按剧本和镜头时长生成，还没有依据真实语音逐句对齐。

**演示说法：** “导出提供视频、封面和字幕草稿，视频使用常见编码，方便播放和后续剪辑。”

### 6.6 cryptography与Fernet

**是什么：** cryptography是Python密码学库；Fernet是项目用于对称加密并检查密文完整性的方案。

**项目中干什么：** 模型API Key在服务端加密后保存到数据库。使用时凭独立主密钥解密，回读到页面的配置不包含长期保存的明文Key。

**具体例子：** API与Worker必须能读取同一套配置并使用正确主密钥，否则有配置记录也可能无法调用供应商。

**边界：** 加密不是简单哈希；凭据要在调用时取回，所以使用可解密方案。数据库备份与主密钥要配套，单有密文不能恢复凭据。存储加密也不等于网络已经使用HTTPS。

**演示说法：** “API Key保存在服务端密文中，执行器按权限解密使用，页面回读配置时看不到保存的明文。”

## 7. 模型接入与流式输出

### 7.1 Provider Adapter

**是什么：** 项目自己编写的供应商适配代码，把业务输入翻译成某家服务的请求，并把响应转换成统一资产或作业状态。

**项目中干什么：** 隔离百炼、OpenAI兼容图片服务、不同H3服务等协议差异。模型库决定选谁，适配器决定怎样请求。

**具体例子：** 仙宫云使用multipart、`prompt_id`和鉴权下载；另一家服务可能使用JSON提交和不同任务查询接口。页面仍处理镜头、候选、采用等业务概念。

**边界：** 适配器统一调用入口，不能把不支持图生图的模型变成支持，也不能保证不同供应商画质一致。

**演示说法：** “换供应商主要处理接口协议和能力差异，项目、角色和镜头制作流程可以继续复用。”

### 7.2 模型库与用途绑定

**是什么：** 服务端保存连接、模型、协议参数和用途映射的配置机制。

**项目中干什么：** 把故事、剧本、图片、图片编辑、视频提示词和镜头视频分别绑定模型，并保存配置版本。

**具体例子：** 故事使用文本模型，角色整板使用图片模型，视频使用已部署的仙宫云H3。不能只填一个地址就推导出所有用途都可用。

**边界：** 模型名称只是服务要求的标识，不等于自动获得对应能力；通用JSON参数不能替代还没实现的协议。

**演示说法：** “可以按阶段选适合的模型，配置版本也会记录到作业里。”

### 7.3 Skill、提示词模板与风格快照

**是什么：** 项目使用的文字规则、模板和本地处理代码，不是重新训练的模型，也不是一个独立GPU服务。

**项目中干什么：** 按用途组织剧本或视频输入，约束人物描述、材质、光影、台词与参考素材。风格快照把项目创建时的规则保存下来。

**具体例子：** 港风武侠预设提炼低饱和青灰、胶片光影和防人类兽化要求，但不把谢逊金发或张翠山兵器写成所有人物的共同设定。

**边界：** 参考图用途优先清晰身份，不能把剧情昏暗布光无条件搬进去。规则更新不会自动重画旧图片或改变已经生成的视频。

**演示说法：** “提示词规则让输入更具体，风格快照让同一个项目持续使用同一套视觉要求。”

### 7.4 仙宫云与MiniMax H3

**是什么：** 仙宫云提供远端运行环境；已部署的H3应用提供视频生成API。ComicFlow连接这个应用，管理输入和结果。

**项目中干什么：** 按当前模式上传素材和参数，保存`prompt_id`，查询任务，鉴权下载视频，存入MinIO后成为候选。

**边界：** 业务服务器与GPU实例不必是同一台机器。关闭GPU实例会影响新的生成和查询，已保存到业务对象存储的媒体仍可使用，前提是业务服务和存储正常。

**演示说法：** “GPU服务负责生成视频，项目系统负责把镜头和素材送进去，再保存和管理返回结果。”

### 7.5 JSON、HTTP、鉴权与multipart

| 概念 | 解释 | 项目用途 |
| --- | --- | --- |
| HTTP | 客户端与服务端交换请求和响应的协议 | 浏览器访问API，后端访问模型 |
| JSON | 用文本表示对象、列表、数字等数据的格式 | 传项目、镜头、配置及接口结果 |
| GET | 常用于读取数据的请求方法 | 查询项目和已有作业 |
| POST | 常用于发起操作或创建记录的请求方法 | 创建作业、发起拆分 |
| PUT/PATCH | 常用于保存或更新数据的方法 | 保存预览或编辑剧本，具体以接口为准 |
| API Key / Bearer | 服务鉴权凭据及常见传递方式 | 服务端获准访问供应商API |
| multipart/form-data | 同一请求同时携带文字字段和文件的格式 | 上传H3参考图片和生成参数 |

JSON不是模型，也不是接口协议的全部。即使JSON格式正确，路径、模型名、鉴权、参数范围或响应映射错误，仍可能无法调用。

### 7.6 SSE、fetch、StreamingResponse与心跳

**是什么：** SSE是一种由服务端持续向客户端发送文本事件的HTTP方式。项目使用浏览器`fetch`读取POST响应流，而不是用只能直接发GET的原生EventSource处理这一入口。

**项目中干什么：** 前端声明`Accept: text/event-stream`；FastAPI以`StreamingResponse`持续发送`phase`、`delta`、`result`或`error`。浏览器解码收到的数据并更新正文及状态。

**具体例子：** 模型返回第一段文字后显示第一段，继续返回后继续显示；完整结果通过检查后才进入可保存预览。没有内容时约10秒发心跳注释，表明连接仍有反馈。

**边界：** 流式改善等待体验，不减少模型实际计算量。关闭流式的配置或不支持的映射仍可能整段返回。心跳不是生成百分比，文字增量也不是模型内部推理。

**演示说法：** “内容是随模型返回逐步展示的，最后仍会检查完整结果，半段文字不会直接成为正式剧本。”

### 7.7 轮询与WebSocket的区别

**轮询：** 页面或后端隔一段时间主动请求已有任务状态。媒体供应商查询和部分页面状态采用这种方式。

**SSE：** 在一条HTTP连接里由服务器持续返回事件，当前主要用于故事和拆分文本反馈。

**WebSocket：** 允许长期双向通信的协议；不能因为系统有实时反馈就说当前所有进度已经使用WebSocket。

**演示说法：** “文本采用流式返回，媒体作业按接口查询进度，两种方式服务于不同的生成过程。”

## 8. 部署技术：负责让应用在服务器上运行

### 8.1 Docker、镜像与容器

**是什么：** Docker把应用和运行依赖打包成镜像，启动后成为容器。镜像是可运行的软件包，容器是运行中的实例。

**项目中干什么：** 后端镜像包含Python依赖、源码、FFmpeg与字体；前端构建镜像把源码打包，运行镜像用Nginx提供页面。API、Worker、Beat以不同进程承担职责。

**边界：** 容器启动不等于业务健康；镜像也不自动包含对象存储数据和外部数据库。数据卷用于保留需要长期保存的内容。

**演示说法：** “代码和依赖按镜像部署，服务进程分开运行，减少机器环境差异。”

### 8.2 Docker Compose与restart policy

**是什么：** Compose描述多个服务的启动配置、网络、卷和环境；restart policy规定容器退出或Docker重启后的恢复行为。

**项目中干什么：** 管理API、Worker、Beat等组件。本地当前这三个服务使用`unless-stopped`，未被手动停止的容器会随Docker恢复。

**具体例子：** 之前本地Worker/Beat的restart=no，电脑重启后没恢复；本次修复同步修改了容器实际策略和本地Compose文件。

**边界：** unless-stopped不能保证Docker Desktop一定已经启动；手动stop的容器仍需明确start。不能在未检查历史付费作业时随意启动另一套消费者。

**演示说法：** “多个组件有统一运行配置，同时需要检查接口、执行器与调度器各自的状态。”

### 8.3 Nginx、反向代理与同源

**是什么：** Nginx提供静态文件，也可以把请求转发给后端。浏览器同源指协议、主机和端口一致。

**项目中干什么：** 服务器页面请求`/api`，Nginx转发到API；对象存储读取按已配置路径代理。文本SSE相关代理关闭缓冲，避免收到所有文字后才一次性交给浏览器。

**具体例子：** 用户访问一个业务入口，不需要手动分别打开API和MinIO地址。

**边界：** 同源代理不等于已完成完整安全认证。关闭代理缓冲改善流式传输，无法让一个不支持流式的模型开始逐字返回。

**演示说法：** “Nginx提供统一网页入口，并把数据和素材请求送到对应服务。”

### 8.4 Git、GitHub与Drone CI/CD

**是什么：** Git记录代码版本，GitHub保存远端仓库，Drone按流水线执行检查与部署。CI是持续集成检查，CD是持续交付或部署流程。

**项目中干什么：** 当前前后端分别发布，main分支push触发原有流水线，先检查，再构建和更新服务。日常步骤见[Drone提交手册](DRONE_SUBMISSION_RUNBOOK.md)。

**边界：** Git提交、远端推送、Drone触发、检查通过、部署成功和业务验收是不同状态。源码进了Git不代表服务器已经加载。用户已提出后续可直接更新原服务器，具体操作另按授权和连接条件处理，本手册没有执行发布。

**演示说法：** “代码有版本和自动检查，发布后还要验证接口、执行器和浏览器行为。”

### 8.5 宝塔、环境变量与Secret

**是什么：** 宝塔是服务器管理面板；环境变量传递运行配置；Secret用于在发布平台中管理敏感配置。

**项目中干什么：** 原服务器通过现有容器链路运行，后端发布使用`backend_external_env`等配置连接外部数据服务。模型配置主密钥也要独立管理。

**边界：** 宝塔是管理入口，不是FastAPI框架或视频生成模型。代码发布不能默认上传本机项目数据、数据库密码和解密主密钥。

**演示说法：** “服务器运行地址和凭据通过配置管理，代码与敏感数据分别处理。”

| Mypy | 静态检查Python类型 | 检查模块接口和参数类型 | 运行时网络不会失败 |
| Ruff | 检查Python规范与常见错误 | 导入、未使用变量、部分错误模式 | 业务逻辑完全正确 |
| Mock Provider | 返回可控的模拟结果 | 离线检查完整流程与调用次数 | 真实供应商质量和稳定性 |
| 隔离集成测试 | 真数据库/队列/存储配假供应商 | 验证组件连通、重启与保存恢复 | 已完成正式数据迁移 |

**演示说法：** “程序行为用自动测试和真实数据组件验证，模型结果质量用实际样片验证。两个结论分别说明。”

`hatchling`属于Python打包工具，`@vitejs/plugin-react`和`@tailwindcss/vite`属于构建插件，`@types/react`等提供类型声明。这些辅助依赖支持安装、构建和开发，不是额外的产品服务。

## 10. 三个完整流程：把技术与按钮对应起来

### 10.1 点击“拆分剧本”之后

| 步骤 | 实际工作 | 主要技术 | 用户能看见什么 |
| --- | --- | --- | --- |
| 1 | 前端读取故事、目标时长和当前项目 | React、Zustand、查询数据 | 故事输入与拆分按钮 |
| 2 | 发起原有POST预览请求，支持时声明SSE | fetch、HTTP | 开始等待 |
| 3 | API检查请求与项目，进入故事/剧本业务 | FastAPI、Pydantic | 校验错误或进入生成 |
| 4 | 按script用途选择文本模型，组织消息 | 模型库、Provider Adapter、规则 | 当前阶段提示 |
| 5 | 发起一次文本拆分请求，读取增量 | HTTPX、文本供应商 | 正文逐步出现 |
| 6 | 通过同一响应流回传增量和事件 | asyncio、StreamingResponse、SSE | 输出和等待状态 |
| 7 | 完整返回后检查结构、角色引用和时长等 | 消息契约、业务程序 | 可保存预览或错误 |
| 8 | 用户保存预览，检查expectedVersion | API、Repository、PostgreSQL | 正式编辑区内容更新 |
| 9 | 编辑并确认剧本，本地业务校验 | 后端规则、数据库 | 进入下游阶段 |

后续本地结构检查不是再发一个AI审查请求。保存预览和确认剧本不重新调用文本模型。输入审核是另一项职责，需要按具体入口说明，不能仅凭拆分一次就概括整个项目总共只发一次请求。

**现场讲解：**

> “这里先让模型把故事转成场景和镜头，同时把真正返回的内容逐步显示。结果完整后，程序检查它能否用于后续制作。用户满意才保存，不满意的预览不会直接覆盖原剧本。”

### 10.2 点击“生成角色文字设定板”之后

| 步骤 | 实际工作 | 主要技术 | 持久记录 |
| --- | --- | --- | --- |
| 1 | 前端提交角色、text-board用途、版本和操作ID | React、HTTP、UUID工具 | 操作身份 |
| 2 | 检查角色字段、版本、尺寸及绑定模型 | FastAPI、Pydantic、业务规则 | 通过后准备作业 |
| 3 | 冻结外观、服装、风格及配置版本 | 图片作业模块 | 输入快照、revision |
| 4 | 在同一事务保存作业与outbox | SQLAlchemy、PostgreSQL | 作业和pending事件 |
| 5 | Beat定期发派发消息，Worker派发outbox | Beat、Celery、Redis | 事件派发状态 |
| 6 | Worker领取作业并核对输入、配置、租约 | Repository、图片作业模块 | 状态与检查点 |
| 7 | 按图片协议提交冻结输入 | Provider Adapter、HTTPX | 调用计数、上游任务号（若有） |
| 8 | 查询或接收结果，保存图片并检查 | MinIO、Pillow | 文件引用、结果记录 |
| 9 | 页面查询作业并显示候选 | TanStack Query、React | 成功状态与候选 |
| 10 | 用户检查并确认候选 | 角色业务、PostgreSQL | 当前采用参考 |

text-board直接使用保存的外观和服装，不额外调用文本润色模型，不要求先生成主图。普通情况下这条用途生成一张整板，但实际是否调用、恢复到哪一步应看作业记录，不能对所有历史三视图用途都承诺只调用一次。

2026-10-08本次恢复实例：作业`ijob_e490a61cd6ef412589c01a7b507fa353`，结果succeeded，attempts=1、callsStarted=1，图片1536×1024，存储内容读取通过。卡住发生在执行器未运行阶段，最初调用次数为0，并不是图片模型一直在计算。

**现场讲解：**

> “人物设定先保存为结构化数据，生图时把外观、服装和风格冻结成这次作业的输入。后台生成并保存候选，用户确认后再给视频使用。生成完成与质量确认是两个步骤。”

### 10.3 从“生成镜头视频”到“导出”

| 步骤 | 实际工作 | 主要技术 |
| --- | --- | --- |
| 1 | 检查镜头、角色、场景、连续性素材和语音预算 | 视频准备单、业务规则 |
| 2 | 展示实际输入、像素、时长和模式，记录指纹 | 前端准备单、确定性输入整理 |
| 3 | 用户提交后核对指纹，创建持久视频作业 | FastAPI、PostgreSQL、outbox |
| 4 | Worker领取作业，按固定配置读取素材字节 | Celery、Repository、MinIO |
| 5 | 上传H3参数、参考图和reference_manifest | HTTPX、multipart、H3 Adapter |
| 6 | 保存prompt_id并查询已有任务 | 视频检查点、供应商API |
| 7 | 鉴权下载，保存视频、必要元数据和候选 | HTTPX、MinIO、PostgreSQL |
| 8 | 用户播放并采用满意结果 | React、采用业务 |
| 9 | 导出读取有效镜头，核查长度、规格和音轨 | Worker、MinIO、ffprobe |
| 10 | 归一、裁剪、按顺序拼接并处理原声 | FFmpeg |
| 11 | 保存video.mp4、cover.jpg、subtitles.srt | MinIO、项目导出记录 |

默认中文确定性路径发送`compile_prompt=false`，关闭远端二次编译；选择需要文本模型的视频提示词路径时，可能另外产生文本调用，应以准备单及作业记录为准。

合成使用已有有效素材，不暗中生图、生视频或补齐缺失媒体。候选不满意时先保留，用户决定是否另行生成。字幕仍是草稿，原声台词是否准确仍需试听。

**现场讲解：**

> “视频生成前先核对实际输入，后台管理远端任务，结果保存后先试听和观看，再采用。导出阶段复用已采用镜头，通过FFmpeg加工交付，不再把整条作品交给模型重新生成。”

## 11. 每个产品模块的输入、输出与技术

| 模块 | 输入 | 主要处理 | 输出 | 主要技术 |
| --- | --- | --- | --- | --- |
| 创建 | 创意或故事、目标时长、风格 | 创建项目，按需要扩展故事 | 项目与故事 | React、FastAPI、文本Adapter、数据库 |
| 剧本 | 故事、制作要求 | 拆分、流式反馈、规范化、预览和编辑 | 可确认的场景/镜头数据 | SSE、文本模型、消息契约、版本检查 |
| 分镜 | 已保存剧本 | 按镜头显示制作信息、定位编辑 | 镜头制作清单 | React、Zustand、同一份剧本数据 |
| 角色 | 外观、服装、身份、风格 | 提示词按用途整理、参考图或整板生成 | 角色卡与候选/确认参考 | 图片Adapter、持久作业、MinIO、Pillow |
| 风格 | 预设和项目选择 | 保存规则快照，按用途应用 | 项目视觉规则 | 本地结构化规则、数据库 |
| 画面 | 镜头、有效参考、生成配置 | 准备单、作业、远端生成、采用 | 当前有效镜头视频 | H3 Adapter、Celery、Redis、MinIO |
| 声音 | 镜头台词与已有音轨 | 试听，复用原声或执行所选声音路径 | 声音资产/时间轴信息 | 音频业务、FFmpeg、对应Provider |
| 导出 | 已采用且有效的镜头 | 核查、归一、拼接、封面与字幕 | MP4、JPEG、SRT | ffprobe、FFmpeg、MinIO |
| 资源 | 当前可访问项目的历史视频 | 列表、播放和下载 | 历史素材访问 | API、数据库引用、签名URL |
| 模型API | 地址、凭据、模型、协议、用途 | 校验、加密、版本化配置 | 可选用途绑定 | Pydantic、Fernet、模型库 |

声音模块存在Provider边界不代表所有真实TTS和口型供应商均已完整验证。当前H3视频原声路径通常不需要额外配音或口型调用。

## 12. 演示时常遇到的术语

| 术语 | 用普通话怎么解释 |
| --- | --- |
| 前端 / 后端 | 用户操作的界面 / 执行规则并提供数据的服务 |
| API | 程序之间约定的调用入口 |
| Schema | 数据应包含哪些字段、允许什么类型的规定 |
| Snapshot | 某一时点的完整数据或配置快照 |
| Revision / Version | 配置或项目的版本编号 |
| Asset | 图片、视频、声音等资产及其记录 |
| Object key | 文件在对象存储中的定位名称 |
| Transaction | 一组数据库写入一起提交或一起回滚 |
| CAS / 条件更新 | 只有记录仍符合预期时才更新，防止并发覆盖 |
| Idempotency / 防重 | 重复处理同一逻辑操作时识别已有结果，避免多做一次 |
| Queue | 待执行消息的传递通道 |
| Polling | 每隔一段时间查询状态 |
| Checkpoint | 已执行阶段的保存记录 |
| Lease | 某个执行者在一段时间内领取作业的凭据 |
| Candidate / Adoption | 待检查的生成结果 / 用户明确选用结果 |
| Invalidation | 数据改动后，相关旧素材不再适合当前制作 |
| Preflight | 真正生成前对输入、素材与参数的检查 |
| Native audio | 视频模型生成结果本身包含的声音 |
| TTS | 把文字转换成语音的能力 |
| FPS | 视频每秒显示多少帧 |
| Resolution | 图像像素规格，如1536×1024 |
| Inference | 模型根据输入生成结果的过程 |
| Training | 用数据调整模型参数；当前项目没有自行训练模型 |

## 13. 故障从哪里判断

| 现象 | 先检查哪里 | 为什么 |
| --- | --- | --- |
| 页面无法打开 | 前端服务、Nginx、端口 | 页面程序可能尚未提供 |
| 页面打开但项目获取失败 | API、代理、数据库、项目访问条件 | 前端运行与数据接口正常是两个条件 |
| 点击生成后一直queued/preparing、调用次数0 | Worker、Beat、outbox、专用队列 | 可能尚未执行，不能直接归因于模型慢 |
| 已有taskId，查询失败 | 供应商状态、鉴权、网络、查询入口 | 应恢复查询已有任务，而非立即重新提交 |
| submitting后无明确结果 | 作业日志与供应商任务记录 | 超时可能发生在提交已被接受之后 |
| 显示成功但图片/视频打不开 | objectKey、存储、签名地址、代理 | 作业状态与文件实际可读性分别检查 |
| 流式直到最后才显示 | 模型stream配置、Adapter、代理缓冲、UI解析 | 任何一层整段返回都会影响展示 |
| 合成失败 | FFmpeg/ffprobe、素材时长、音轨、文件读取 | 合成有自己的输入与工具前置条件 |
| 模型配置存在但无法使用 | 用途绑定、协议、凭据、原主密钥、revision | 保存配置不等于执行器可解密并正确调用 |

接口health正常只能说明对应健康检查通过；Worker pong说明执行器可响应控制消息；完整生成成功还需要验证作业、供应商、存储及页面读取。当前单进程Worker执行长任务时pong可能暂时延迟，不能仅凭一次超时就断定Worker已停止。
