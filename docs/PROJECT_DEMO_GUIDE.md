## 1. 先记住这段介绍

### 30 秒版本

> ComicFlow 是一个把中文故事转成可编辑剧本，再制作角色参考图、动态镜头并合成视频的创作工作台。它把原来分散在几个模型网站和剪辑工具中的步骤串在一个项目里。用户可以在关键环节检查和修改结果，而不是提交一段文字之后只能接受最终视频。

### 2 分钟版本

> 这个项目的输入可以是一句话创意，也可以是已有故事。先生成或整理故事，再把故事拆成场景和镜头，明确角色、动作、对白、旁白与时长。
>
> 剧本确认后，可以为角色制作参考图或整张设定板，把人物外观和服装作为后续视频的参考。每个镜头在生成之前都有准备单，可以看到实际使用的提示词、模型、参数和图片。
>
> 视频生成属于耗时操作，由后端的作业系统负责执行和记录。生成完成先成为候选，检查满意后再采用。这样不满意的新结果不会直接覆盖已经选好的素材。
>
> 最后把采用的镜头通过 FFmpeg 合成视频。H3 路径会保留视频原声，同时导出视频、封面和字幕草稿。文本、图片和视频模型可以分别配置，不需要把所有步骤绑定到同一个供应商。

### 一句话记忆项目流程

```text
创意/故事
  -> 项目与风格
  -> 故事生成或导入
  -> 剧本拆分预览
  -> 用户确认剧本
  -> 角色卡与参考图
  -> 分镜准备单
  -> 生成视频候选
  -> 用户播放并采用
  -> 声音检查与FFmpeg合成导出
```

每个箭头都代表一次明确的交接：上一步的结果成为下一步的输入；需要模型生成的阶段才会产生模型调用；用户确认前的结果不会自动成为当前制作素材。

### 项目解决的实际问题

| 原来的困难 | 本项目的处理方式 | 演示时可以强调的价值 |
| --- | --- | --- |
| 故事、提示词、图片、视频分散在不同工具 | 用项目组织故事、剧本、角色、镜头和资产 | 降低来回复制和整理素材的负担 |
| 生成过程中看不到发生了什么 | 文本进度、媒体作业状态与生成准备单 | 等待过程有反馈，输入可以核对 |
| 换一个镜头就容易丢失人物特征 | 已确认角色参考板、场景参考和连续性素材 | 给模型提供更稳定的视觉依据 |
| 新结果直接覆盖旧结果 | 候选与采用分开，保留历史资源 | 用户可以先判断质量，再替换当前素材 |
| 失败后不知道能不能重新点 | 持久作业、任务号和恢复检查点 | 可以按失败环节处理，减少重复提交风险 |
| 换供应商要改多个页面 | 模型库、用途绑定和 Provider Adapter | 创作流程与供应商协议分开 |

### 2.2 当前讲解中需要避免的表述

- 不说“我们自己训练了 MiniMax 模型”：当前是应用集成，没有训练或微调模型的实现依据。
- 不说“一键必定生成高质量成片”：流程可以推进，但结果质量要人工检查，部分步骤有确认点。
- 不说“人物永远不会变”：参考板和连续性输入提供约束，不能保证生成模型绝对一致。
- 不说“字幕已经逐字同步”：当前字幕来自剧本和镜头时长，还没有语音时间对齐。
- 不说“所有功能都已经在服务器上”：发布状态需要独立核对。
- 不说“网络错误绝对不会重复扣费”：系统采取防重与未知状态保护，供应商是否支持幂等仍影响最终保证。
- 不说“画布模式已经完成”：当前是按生产阶段组织的工作区，不是自由节点画布。
- 不说“每个风格都有示例图”：当前已有风格规则和选择入口，完整示例图库仍是后续需求。

## 3. 推荐的现场演示顺序

建议用 10 到 15 分钟完成主体演示，再留时间回答问题。提前准备一个已有剧本、角色图和镜头视频的项目，让演示不完全依赖现场生成速度。

### 3.1 演示前准备

1. 确认前端能打开，API 能读取项目。
2. 打开准备演示的项目，检查剧本、角色图片、已采用视频和导出结果是否能读取。
3. 确认当前绑定的文本、图片和镜头视频模型，避免只配置了连接但没有用途绑定。
4. 若准备现场生视频，确认仙宫云实例可用，API 和 Worker 都加载同版代码与配置。
5. 检查声音播放、浏览器音量和视频下载。
6. 准备已有镜头或成片作为等待时的展示内容。
7. 在共享屏幕前收起凭据输入、服务配置文件和调试日志。

2026-10-08已修复本地角色图片等待：恢复Worker/Beat，用户指定图片作业已成功，1536×1024，仅一次生图调用。另5个历史作业保留，其旧派发事件已暂停，不会随调度器自动执行。只看已有项目不要求开启执行器；现场生成必须确认执行器就绪，不能把“网页打开了”当作“生成服务已就绪”。详情见[运行恢复记录](implementation/character-image-runtime-recovery-2026-10-08.md)。

### 3.2 页面操作与可直接讲的话

| 顺序 | 页面及操作 | 可以直接说的话 | 预计时间 |
| --- | --- | --- | --- |
| 1 | 打开已有项目，说明顶部状态 | “所有创作内容围绕一个项目保存，可以接着上次的工作继续。” | 1 分钟 |
| 2 | 创建页，展示故事输入、目标时长和风格 | “先确定项目边界。风格会保存为项目规则，后续角色、场景和视频按用途复用。” | 1 分钟 |
| 3 | 故事/剧本页，展示生成或导入的故事 | “故事是原始输入，接下来要把它变成可制作的结构。” | 1 分钟 |
| 4 | 点击或展示剧本拆分预览 | “模型输出场景和镜头，页面实时显示返回内容；这时仍是预览，还没有覆盖正式剧本。” | 2 分钟 |
| 5 | 确认剧本并进入编辑器 | “用户确认后才保存。每个镜头现在都有动作、对白、旁白、时长和视觉要求。” | 1 分钟 |
| 6 | 角色页，展示角色卡和已确认参考板 | “先固定人物身份和服装，再把参考图交给视频模型，降低镜头之间的人物漂移。” | 2 分钟 |
| 7 | 画面页，展示一个镜头的准备单和候选 | “生成前可以核对实际提示词、参考图、模型和参数；生成后先播放候选，再决定是否采用。” | 2 分钟 |
| 8 | 声音/导出页，播放已有镜头并展示导出包 | “采用的镜头才进入合成。FFmpeg复用这些文件，输出视频、封面和字幕草稿。” | 2 分钟 |
| 9 | 最后展示模型 API 设置 | “模型配置按用途绑定，创作流程不直接依赖某一家供应商。” | 1 分钟 |

查看、切换、播放和采用已有候选可以作为不生成新媒体的展示。点击生成故事、拆分剧本、生成图片、生成视频或文本润色等按钮可能调用模型。合成不调用模型，但会执行本地计算和写入导出文件。

### 3.3 按这条主线讲清楚每一步

| 阶段 | 进入时有什么 | 系统做什么 | 用户要确认什么 | 交给下一阶段的结果 |
| --- | --- | --- | --- | --- |
| 创建项目 | 创意/故事、时长、风格 | 创建项目并保存项目版本、风格快照 | 创作方向和目标时长 | 项目与故事输入 |
| 故事生成或导入 | 一句话创意或现有故事 | 生成、导入或保存故事文本 | 故事方向是否可用 | 故事文本 |
| 剧本拆分 | 故事文本 | 一次文本拆分请求，生成场景和镜头并做程序校验 | 预览结构、人物、动作、台词是否合理 | 尚未保存的剧本预览 |
| 剧本确认 | 已编辑的预览 | 检查版本并写入项目，保留旧版本 | 是否正式进入制作 | 可编辑剧本 |
| 角色准备 | 角色外观、服装、性格 | 生成主图或设定板，保存候选 | 人物脸型、服装、画风是否可用 | 已确认角色参考素材 |
| 镜头准备 | 镜头、角色图、场景图、前镜头素材 | 组装提示词、参考图、时长、分辨率和调用预估 | 实际提交内容是否正确 | 可提交的准备单 |
| 视频生成 | 已确认准备单 | 创建持久作业，Worker调用远端视频服务并保存结果 | 生成中查看状态，完成后播放候选 | 视频候选 |
| 采用与导出 | 用户选中的候选镜头 | 更新当前有效素材，FFmpeg检查并合成 | 是否采用、声音和动作是否合格 | MP4、封面、SRT |

现场可以用这段话串起来：

> “项目先保存创作方向，故事再拆成可编辑剧本；剧本确认后固定人物和镜头输入；镜头生成先形成候选，人工检查后才采用；最后只把采用的有效素材交给合成和导出。这样每一步都有输入、输出和确认点，失败时也能知道停在哪一步。”

现场演示时不要在剧本拆分尚未完成时切换项目。当前拆分请求不会因为切换项目主动取消，但预览保存在当前页面的临时状态中，尚未确认保存的结果可能不会在切回后恢复。已经确认保存的剧本和已经创建的媒体作业不受普通项目切换影响。

### 3.4 如果要现场展示文本流式输出

> “现在显示的是模型真正返回的增量内容，不是前端预写的进度动画。完整结果返回并通过结构校验后，才能进入正式编辑和确认流程。”

供应商或配置不支持流式时，界面会显示等待整段内容，不能保证所有接口都逐字输出。拆分显示的是逐步返回的场景和镜头内容，不等于模型所有内部推理过程。

### 3.5 如果生成需要等待

> “视频不是浏览器本地实时算出来的。后端提交到远端模型服务，记录任务号并查询进度。我们先看这个已经生成的镜头，稍后再回来检查本次作业。”

如果状态是提交结果未知，应讲清楚正在核对供应商记录，不反复点生成。如果远端服务不可用，可以完整演示已有素材的读取、采用和导出流程。

| 异步执行 | Celery 5、Redis、Celery Beat | 作业派发、后台执行、临时生成状态与定时派发 | 视频等待和媒体处理交给独立进程 |

虽然使用 Python 并方便以后连接模型生态，当前依赖与实现并不是一个内置 PyTorch 模型训练平台。仙宫云远端的模型服务是另一套运行环境。

## 5. 整体架构怎样工作

采用“模块化单体 API + 独立 Worker”。API 内部按业务职责拆模块，并非每个页面对应一个独立微服务。

```text
浏览器：React 工作台
    |
    | HTTP API / 文本 SSE
    v
FastAPI：请求校验、项目权限、业务操作
    |
    +--> Production：故事/剧本、角色、准备单、作业、合成
    |        |
    |        +--> PostgreSQL：项目与角色、版本、作业、outbox
    |        +--> Provider Adapter：转换不同模型的请求与响应
    |        +--> MinIO/S3：资产与导出文件
    |
    +--> outbox 派发 --> Redis/Celery --> 独立 Worker
                                           |
                                           +--> 远端模型服务
                                           +--> FFmpeg 媒体处理
                                           +--> 保存状态与资产
```

文本生成的当前入口可以直接通过 API 请求返回流式结果；不要把所有操作都描述成必然经过 Celery。图片、视频等持久作业和合成则使用相应后台执行路径。

### 5.1 前端如何组织

`App.tsx` 根据当前工作区选择功能组件，用 TanStack Query 获取项目快照。`AppShell.tsx` 提供导航、项目状态、模型设置和项目选择入口。

Zustand 保存当前项目和选中镜头等界面状态，项目 ID 会写入浏览器 `localStorage`，方便重新打开。故事、剧本、媒体和生成结果不以浏览器缓存作为正式存储。

进行中的部分项目状态通过轮询刷新；故事与剧本生成在支持时使用 SSE。当前并非所有进度都通过 WebSocket 推送。

### 5.2 后端如何组织

- `api/`：路由、请求 schema、访问检查和响应。
- `production/`：故事剧本、角色素材、镜头准备、作业、采用与合成等业务。
- `providers/`：文本、图像、视频、存储和 FFmpeg 等外部能力适配。
- `infrastructure/`：数据库、作业存储、Redis 命名空间和临时状态。
- `worker/`：Celery 入口、outbox 派发和后台执行。
- `domain/`：公共领域类型与业务错误。

可以这样说：

> “页面不直接拼供应商请求。API 先进入业务层，准备好项目数据，再交给适配器。这样换供应商时主要改协议接入，项目和创作流程能够继续复用。”

### 5.3 数据分别存在哪里

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 故事、剧本、项目阶段、资产引用 | PostgreSQL 的项目状态记录 | 当前大量项目内容使用 JSON payload，并不是每个镜头都有独立关系表 |
| 角色外观、服装、声音设定和参考引用 | PostgreSQL 角色记录 | 角色有版本信息，供下游核对 |
| 图片与视频作业 | 独立作业表 | 保存状态、输入快照、操作标识、检查点与结果 |
| 模型连接、模型参数、用途绑定 | 模型配置版本表 | 保留 revision 与加密凭据 |
| 待派发业务事件 | PostgreSQL outbox 表 | 与相关业务写入配合，随后发布到队列 |
| 队列消息、结果、事件和临时生成状态 | Redis | 不替代 PostgreSQL 中的正式项目记录 |
| 图片、视频、音频、封面和字幕文件 | MinIO/S3 | 数据库保存 objectKey 等元数据与引用 |
| 当前打开的项目 ID 等选择 | 浏览器 localStorage/Zustand | 属于浏览器使用状态 |

## 6. 每个功能具体怎么实现

### 6.1 创建项目与故事生成

用户选择创作输入、目标时长和风格后创建项目。业务层建立项目 ID、初始阶段与必要的会话数据，保存到配置的持久化运行时。

需要扩展故事时，服务端根据模型库的 `story` 用途选择文本模型。模型完成后，内容经过相应消息契约处理，写入项目的故事文本。直接编辑并保存故事属于数据操作，不自动触发新故事生成。

> “先把创意变成可确认的故事，再进入镜头拆分，避免直接从一句话跳到几十个不可控的视频任务。”

### 6.2 剧本拆分、预览与确认

故事通过文本模型拆成结构化剧本，核心包括场景、镜头、人物引用、时长、动作、对白、旁白和声音描述。

当前前端常用流程是：

```text
已有故事
  -> POST script/preview：一次文本拆分请求
  -> 本地规范化和校验
  -> 展示预览
  -> PUT script/preview：用户保存预览
  -> 编辑并保存剧本
  -> POST script/confirm：校验并确认
```

预览与正式写入分开，避免不满意的拆分直接覆盖原剧本。保存时携带 `expectedVersion`，用于发现当前项目是否已被其他操作修改。

单次拆分操作保持一次文本生成请求。后续结构校验使用程序完成，不为无效输出隐式追加模型修复请求；确认剧本不重新调用文本模型。输入审核与拆分是不同职责，不能把“单次拆分”解释为整条链路任何时候都只有一次网络请求。

当前已删除的“AI 剧本分析”只是固定评分与建议面板。真实结构校验仍保留，但不代表存在另一个 AI 剧本质量评分功能。

> “这一步负责把叙事变成后续可执行的数据。模型负责创作，程序负责检查字段和引用，用户负责确认内容。”

### 6.3 流式输出怎样实现

前端通过 `fetch` 读取 POST 响应流，并声明 `Accept: text/event-stream`。服务端使用 FastAPI `StreamingResponse` 在同一个请求中返回事件。

| 事件 | 用途 |
| --- | --- |
| `phase` | 等待首段、正在输出、整段等待、正在校验等阶段 |
| `delta` | 模型本次新增的文本 |
| `result` | 完整操作的最终结果 |
| `error` | 安全处理后的业务错误 |
| 心跳注释 | 长时间没有内容时保持连接反馈 |

界面显示等待秒数和可读内容，最终成功前不能把半段结果当作可确认剧本。代理配置关闭缓冲，避免服务端流式发送而浏览器最后一次性看到。

标准兼容协议支持真实增量；显式关闭流式或使用不兼容映射时仍可整段返回。断线不自动再发一次生成请求；原操作尽量继续执行，但进程内任务不等于能跨服务崩溃恢复的持久文本作业。

### 6.4 分镜编辑

分镜以镜头为单位展示剧本中的制作信息。选择镜头后可以回到对应场景编辑，当前选中镜头由前端状态管理。

它和剧本引用同一套镜头数据。一个镜头的动作、台词或时长变化会影响下游素材，不能把修改文字理解成已有视频同步改变。

> “分镜是把剧本变成制作清单：每个镜头拍什么、人物做什么、说什么、持续多久，都能逐项核对。”

### 6.5 角色卡与角色图片

角色卡保存名字、外观、服装、性格、声音等身份信息。角色图片入口按用途选择已有能力：

| 用途 | 实现方式 | 前置条件 |
| --- | --- | --- |
| 单张主图 | 按角色提示词或保存的设定调用图片模型 | 角色设定已保存 |
| 文字设定板 | 按保存的外观、服装和项目风格，一次生成含脸部特写与全身正侧背视角的整板 | 使用图片生成绑定，不要求先有主图 |
| 基于主图的参考板 | 把已确认主图交给图片编辑能力制作多视角整板 | 主图已确认、图片编辑用途已绑定 |

文字整板不额外调用文本模型，也不暗中使用已有主图。图生图整板则必须传入主图；两者不是同一个请求换了按钮文案。

生成结果先作为候选，确认后才成为视频可用参考。人物设定或素材来源改变后，旧候选可能失效，防止用新角色文字配旧参考板。

参考板的作用是明确身份与服装，不需要复制剧情中昏暗、遮挡的摄影效果。模型是否正确画出同一人物的多角度，仍要人工检查。

### 6.6 风格库如何影响生成

当前本地目录有 10 种预设：真人电影写实、国风三维动画、日系二维动画、国风厚涂、水墨动画、美式漫画、真人纪实 DV、克制悬疑摄影、电影色彩对比、港风武侠胶片。

每个风格包含媒介类型、材质表现、光影、运动要求与避免项。创建项目时保存风格快照和版本，旧项目继续使用自己的规则，不因为目录更新被悄悄改变。

同一套规则按生成用途调整：

- 剧本：影响视觉描述，不改写人物台词或添加事件。
- 角色参考：清晰五官、服装和身份，中性背景与均匀布光优先。
- 场景参考：无人广角环境，明确空间、光源和可行走路径。
- 视频：服从原镜头的动作顺序、对白和运动。

港风武侠规则提炼了青灰低饱和、胶片颗粒、柔和逆光与真实材质，也保留了“不能因绰号把人类兽化”等约束。没有把谢逊的金发、张翠山的兵器、特定天气或 2:3 画幅固化成所有项目的要求。

> “风格库保存的是可复用的视觉规则，不是把某个角色的整段提示词复制给所有角色。”

网页上的 Image 2/2.5 名称和提示词来源不决定实际调用哪一个模型。运行时使用模型库绑定和对应协议；Midjourney 的 `--stylize` 等参数也不能直接套到其他 API。

### 6.7 视频生成准备单

准备单读取当前镜头、已确认角色素材、场景参考、前镜头连续性素材和模型配置，组装实际生成输入。

它展示模型、模式、时长、分辨率或实际像素、提示词、素材引用以及预计文本/视频调用。常见检查包括缺少参考素材、版本改变、语音预算和供应商模式约束。

准备阶段本身不提交视频生成，也不先做付费文本扩写。规则路径若需要文本扩写，会在实际作业中执行并记录。准备单指纹与生成时再次计算的指纹不一致时，要求重新核对，避免用户检查了旧输入却提交新内容。

> “这张准备单让我们能回答：这个视频到底用了什么文字、哪些图片、什么参数。”

### 6.8 仙宫云 MiniMax H3 怎样接入

仙宫云是远端模型服务环境，ComicFlow 是创作与作业管理应用。项目通过独立 `xiangongyun-h3` 适配器连接已部署的服务，没有把本机业务数据库放到 GPU 实例上。

```text
读取镜头与参考素材
  -> 本地组织中文创作输入
  -> 读取图片实际字节
  -> multipart POST /api/v1/jobs
  -> 保存返回的 prompt_id，作为供应商任务号
  -> GET /api/v1/jobs/{prompt_id} 查询
  -> 鉴权下载 /api/v1/output
  -> 保存到 MinIO
  -> 返回视频候选，等待采用
```

参考图片通过 multipart 文件上传，`reference_manifest` 把素材与提示词里的引用标签对应起来。当前支持文生视频、首帧、尾帧、首尾帧与多参考图等既有模式，并验证模式之间的限制。

默认中文路径采用本地确定性整理，明确发送 `compile_prompt=false`，关闭远端二次编译。这是为了降低台词被远端再改写的风险，不代表视频模型必定逐字说对。

另一条 `local-skill` 路径会使用视频提示词文本模型与本地规则，需要单独考虑文本调用。演示时以准备单显示的实际模式为准。

仙宫云当前适配器使用 `0.4P` 到 `1.0P` 的档位与实际像素映射，默认 `0.5P` 的竖屏为 `544×960`；支持 `9:16` 和 `16:9`。不能与另一个 H3 服务的 `768P/1080P/2K` 档位混为一谈。请求时长要求为 4 到 15 整数秒，普通参考图最多 9 张。

下载地址受同源和路径检查，并携带鉴权，不把任意返回 URL 当作可信下载地址。已知任务号后恢复只查询或下载，不再次提交一个生成任务。

> “接入的核心是 API，但产品还需要把人物图片、镜头输入、任务状态、结果保存和错误恢复一起接好。”

### 6.9 如何处理镜头连续性

连续性依靠结构化动作、已确认角色参考、场景参考和相邻镜头尾帧等输入，不是一个额外承诺百分之百成功的 AI 导演。

动作采用起始、中间、结束等状态描述，强调模型应完成到要求的终点。同场景后续镜头可以使用前一个有效视频的尾帧，帮助位置、姿态和环境衔接。

H3 普通参考图与首尾帧不能任意混用。当前源码在后续镜头有角色参考且没有显式关键帧时，会采用参考重锚定，把上一尾帧作为普通连续性参考，与角色素材一起传入；不满足这一条件的路径再按规则考虑首帧衔接。不要把旧记录中的“仅新角色进入才重锚定”作为当前所有路径的准确描述。

前镜头尚未采用、没有尾帧或依赖已经失效时，后镜头准备会阻断，不能悄悄丢掉连续性输入继续生成。

### 6.10 耗时作业、防重与恢复

视频作业保存操作 ID、项目版本、输入指纹、模型配置版本、状态、任务号、调用记录与检查点。数据库中的操作键与活动位置约束、执行租约等机制共同减少重复执行。

| 状态或情况 | 系统怎样处理 |
| --- | --- |
| 排队或准备中 | Worker 获取作业，读取固定输入并执行 |
| 已提交且拿到任务号 | 保存任务号，继续查询已有任务 |
| 查询或下载中断 | 在满足恢复条件时继续对应阶段 |
| 提交开始后未拿到确定响应 | 保留未知状态，不自动再提交 |
| 模型完成 | 保存文件与候选，不直接覆盖当前采用结果 |
| 项目或配置变化 | 检查输入和版本，拒绝不安全地沿旧输入继续 |

Celery 队列允许消息再次投递，所以不能只靠“收到消息一次”保证安全。数据库与检查点负责识别重复或已经执行的工作。供应商幂等能力也是外部约束，不能宣称跨网络绝对 exactly-once。

Outbox 的含义是：相关业务记录和待派发事件写入数据库，再由派发器发到 Celery。当前 Beat 配置每 2 秒调度派发。它降低“业务已写入但任务没发出去”的遗漏风险，消息重复仍需业务防重处理。

### 6.11 采用、局部修改与历史素材

生成成功表示模型返回了可保存的结果；采用表示用户决定把它用于当前制作。两者是不同状态。

采用后切换当前有效素材，并处理依赖它的时间轴、导出或后续素材。保存剧本修改时保留历史版本，撤销受影响媒体的当前有效状态；根据已有尾帧依赖传播失效。文件和无关镜头不会因此被一律删除，也不会自动发起新生成。

当前失效传播有明确实现范围，不能宣称任何历史数据和任何入口都已建立完整依赖图。已有依赖缺失的数据仍需单独判断。

> “改错一个镜头不需要从故事开始重做，但依赖它的内容必须重新检查。旧文件保留，当前制作不会误用过期结果。”

资源页用于查看当前有权访问项目的历史视频。历史浏览、播放和下载不等于重新采用，也不是全站公开素材市场。

### 6.12 声音与字幕

H3 生成的视频可能已经包含对白、旁白与环境声。当前 H3 合成路径优先复用有效视频的原音轨，不要求先提取 WAV，也不自动再调用 TTS 或口型生成覆盖原声。

对白与旁白是要说出的文字；环境声保存在声音描述中。无语音镜头允许对白和旁白为空字符串，不能为了通过校验把“雨声”“脚步声”等补成旁白。

声音页可以试听已有视频并检查剧本文字。修改台词只修改业务数据，不会改变已经生成的视频声音；要让新台词进入视频，需要重新生成对应媒体并验收。

字幕按剧本和镜头时长生成 SRT 草稿，尚未用语音识别或强制对齐校准逐句时间。有音轨也不等于说话人、发音和台词内容已经正确。

### 6.13 合成与导出

使用已有有效素材执行 FFmpeg 处理，不通过文本、图片或视频模型补缺失媒体。

```text
读取镜头顺序和计划时长
  -> 从对象存储读取当前有效视频
  -> ffprobe 检查视频、长度和音轨
  -> 裁剪并归一画面与音频
  -> 拼接镜头
  -> 提取封面，生成字幕草稿
  -> 保存导出包并提供访问地址
```

当前动态视频合成路径把片段归一到 `1080×1920 / 30fps`，视频编码 H.264、音频 AAC，并输出 `video.mp4`、`cover.jpg`、`subtitles.srt`。该路径是竖屏交付实现，不应由供应商支持横屏推导出所有导出比例都已实现。

输出 1080×1920 表示容器与合成规格，不代表把 544×960 原视频变成了原生 1080P 细节。现有规则会检查素材过短、读取失败和有台词却缺音轨等情况，而不是静默补一张图片或重新调用模型。

字幕作为独立 SRT 文件交付；不能仅因导出包含字幕文件就说视频已经烧录字幕。声音质量、字幕同步和镜头质量仍应人工验收。

## 7. 模型 API 页面为什么分成几个部分

| 概念 | 存什么 | 示例说明 |
| --- | --- | --- |
| 连接 | 服务基础地址、名称、凭据 | “这个供应商在哪里，如何鉴权” |
| 模型 | 模型标识、协议、参数与启用状态 | “用哪个接口格式、时长或分辨率怎么传” |
| 用途绑定 | 故事、剧本、角色提示词、图片、图片编辑、视频提示词、镜头视频等对应模型 | “这个生产阶段选用哪个模型” |

同一个连接可服务多个模型，同一个模型也可能用于多个允许的用途。按用途拆分后可以让故事模型重创作、剧本模型重结构、图片模型重造型、视频模型重动作。

服务端用配置快照隔离请求，作业记录使用的配置 revision，避免后台执行时无意读取到后来刚修改的模型配置。

API Key 使用 Fernet 加密保存在服务端，主密钥独立管理；数据库备份不包含主密钥就不能完成原凭据恢复。浏览器仍会处理用户录入或更新密钥的动作，但不能把服务端长期保存的明文凭据当作前端业务数据返回。

保存配置、绑定用途和预览不是生成调用。“测试连接”需按类型解释：地址可达不等于鉴权成功；选定文本模型的显式短请求测试可能计费；媒体连接不靠自动生图或生视频来伪装无成本测试。

## 8. 部署与工程质量怎样说明

### 8.1 现有发布链路

前后端分别发布到 GitHub 仓库，通过 Drone 的 `main` 分支 push 触发检查与部署。

```text
审核本次差异
  -> 按白名单导出发布文件
  -> 提交对应仓库
  -> GitHub push / Drone 触发
  -> 类型、规范、构建与测试
  -> Docker/Compose 更新服务
  -> 健康检查与浏览器验收
```

服务器前端由 Nginx 提供静态文件，并代理同源 API 请求；后端、Worker 和 Beat 通过配置连接外部 PostgreSQL、Redis 与 MinIO。Redis 使用应用命名空间隔离，逻辑隔离不等于独立实例或完整 Redis ACL。

后端流水线复用 `backend_external_env`，不能混用历史内置数据栈的 Secret。普通代码发布不自动把本机数据库、媒体和密钥打包上传。涉及新后端接口时先发布并验证后端，再发布前端。

> “发布不是把目录直接复制到服务器。先跑检查，再更新容器，最后验证服务和页面。提交成功、构建成功和上线成功是三个不同的确认点。”

日常操作以 [Drone 提交手册](DRONE_SUBMISSION_RUNBOOK.md) 为准。仓库根 README 仍含早期 Node 原型和标签部署描述，不能直接照搬到当前环境。

### 8.2 怎样证明它不是只有界面

- 后端用 pytest 验证业务流转、错误路径、配置、准备单与作业行为。
- 前端用 Playwright 验证按钮、页面状态、编辑、预览与下载等实际浏览器行为。
- Node 测试覆盖部分前端工具逻辑，TypeScript/Mypy 检查类型，Ruff 检查 Python 规范。
- 隔离集成验收用模拟供应商连接真实测试数据库、MinIO 与 FFmpeg，验证合成和恢复。
- 模型结果另做人工质量验收，模拟测试不证明画面和声音质量。

2026-09-24 的已有验收记录为后端 949 通过、3 条条件跳过，前端 82 条浏览器与 45 条 Node 测试通过。这是当时的记录，不是本次重新跑全量的结果，也不是目前服务器版本的测试报告。

2026-10-08 删除静态分析面板后，前端类型检查和构建通过。测试数字适合回答技术追问，不必作为业务演示的主要卖点。

## 9. 演示中常见问题与回答

### Q1：这不就是调用几个 API 吗？

> “模型能力来自 API，但产品工作在于把创作数据、素材、异步任务和交付组织起来。比如人物参考要确认、镜头输入要可核对、失败后要知道有没有创建任务、生成结果要先采用、改剧本后旧素材要失效，这些不是一个请求就能解决的。”

### Q2：为什么不用一个模型做完所有事？

> “故事创作、结构化剧本、图片造型和视频动作需要不同能力。按用途绑定模型，能分别优化质量、成本和速度，后续也方便替换供应商。”

### Q3：角色一致性怎么保证？

> “先保存角色身份，再确认参考板，生成视频时传入实际图片；相邻镜头再结合前镜头的连续性素材。它能提高约束力度，但仍需要检查模型输出，不能保证绝对不变。”

### Q4：为什么生成完还要点采用？

> “生成成功只说明返回了结果，不说明它符合创作要求。先成为候选可以保留现有满意素材，用户选择之后再影响当前时间轴和导出。”

### Q5：网络断了会怎么样？

> “媒体作业保留任务号和检查点。已知任务号时继续查原任务，提交结果不明时先核对，避免立即再发一次。文本流式断线也不自动重发，但它和持久媒体作业的恢复能力不同。”

### Q6：剧本拆分为什么需要等待？是不是反复审核？

> “拆分要让文本模型输出场景和镜头结构，耗时取决于模型和长度。当前一次拆分只发一次文本生成，输出后的校验是程序计算，不再自动追加模型修稿。流式反馈主要让等待过程更清楚，不代表算力速度必然提高。”

### Q7：视频里的声音是另配的吗？

> “H3 路径通常直接使用模型视频里的音轨，合成时保留原声。独立配音属于其他明确入口，不是每个镜头都会再配一次。”

### Q8：字幕会自动跟声音对齐吗？

> “目前是按剧本文字和镜头时长生成草稿，还没有逐句语音时间对齐。可以导出后检查，这部分是明确的后续优化点。”

### Q9：我修改旁白，旧视频会立即变化吗？

> “不会。剧本文字和视频文件是两份不同的数据。修改会影响素材有效性，新台词要在重新生成的镜头里检查。”

### Q10：输出是 1080P，为什么原始生成档位更低？

> “模型档位决定原始素材像素；合成规格决定最终文件尺寸。归一成 1080×1920 方便交付，不等于补出原来没有的细节。”

### Q11：风格库和提示词库有什么区别？

> “这里的风格库是一组材质、光影、色彩、运动和避免项规则，能按用途组合进提示词。它不等于一个已经有大量封面图片和搜索功能的公开提示词市场。”

### Q12：能自动做完一条 30 秒视频吗？

> “系统有生产推进和合成能力，但当前关键点需要确认，尤其生成候选需要采用。完整真实作品还要检查动作、衔接、声音和台词，不能把程序流程通过当作最终质量验收。”

### Q13：仙宫云关机后还能看项目吗？

> “已保存到项目对象存储里的素材不依赖继续开着模型实例。创作系统和数据库、MinIO 要保持可用；新生成与远端任务查询则依赖仙宫云服务。”

### Q14：额度就是供应商扣费吗？

> “内部额度是产品的估算、预留和结算记录，不等于供应商账单。实际成本还涉及文本、图片和视频 API，以及 GPU 实例运行费用。”

### Q15：下一步最值得优化什么？

> “先把真实完整作品的质量和使用流程验证清楚，再完善等待反馈、界面简化、风格示例图和字幕对齐。节点画布可以另行评估，不作为当前完成创作链路的前提。”

## 11. 演示前最后一遍速记

1. 产品：从故事到镜头视频的可编辑创作工作台。
2. 技术：React + FastAPI，PostgreSQL 保存事实，Celery/Redis 执行作业，MinIO 保存媒体。
3. 模型：按用途接入现成服务，通过适配器统一业务调用，没有自己训练模型。
4. 控制：生成前看准备单，生成后先候选再采用，修改后检查下游失效。
5. 交付：FFmpeg 合成已有有效素材，H3 原声复用，输出视频、封面和字幕草稿。
6. 限制：字幕未语音对齐，画质与台词要验收，本地功能不自动等于服务器功能。

### 结束时可以这样说

> “目前已经把故事、剧本、角色参考、逐镜生成和导出组织在一个项目里。接下来最需要实际使用反馈：哪一步难理解、哪种结果不稳定、哪些操作最花时间。我们根据真实创作中的问题继续优化。”
