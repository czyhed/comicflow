# ComicFlow 项目工程规约

状态：生效
最后更新：2026-09-24

这份文档是每次创建任务、拆分任务和修改功能前的必读入口。它记录项目目标、工程规则、关键决策、阶段边界、数据流和验收门禁。若新需求与本文件或 ADR 冲突，先记录决策并更新文档，再修改代码。

## 一、工程规则

1. 每次修复必须定位并修复根因。禁止用重试、前端状态覆盖、固定模板、重复分支或默认降级掩盖错误。临时诊断代码可以存在于本地，但不得作为交付实现。
2. 每次新增功能先阅读本文件、`CONTEXT.md`、相关 `docs/adr/`、相关 spec 和当前实施计划。
3. 先定义目标、范围、数据流、接口、失败行为和验收标准，再拆任务。每个任务必须有独立的输入、输出、测试和验收门禁。
4. 行为变更遵循 RED → GREEN → 回归：先写能证明缺陷的失败测试，确认失败原因正确，再实现最小根因修复，最后运行聚焦测试和全量回归。
5. 技术栈以 ADR 0005 为基线：React + TypeScript + Vite、Python 3.12+ + FastAPI + Pydantic + SQLAlchemy 2 + Alembic、Celery + Redis、PostgreSQL、MinIO/S3 和 FFmpeg。除非新增 ADR，不更换框架或引入新的编排平台。
6. Mock 只用于本地和测试；正式项目状态使用 PostgreSQL，Redis 只保存队列、锁、事件和临时生成状态。不得静默以内存模式替代正式运行时。
7. 修改一个阶段时，必须验证它给下游阶段提供的接口和数据形状，不得只让当前页面看起来可用。
8. 保留现有领域词汇，使用 `CONTEXT.md` 中的“项目、故事、剧本、场景、镜头、资产、生产阶段、确认点、生成作业”等术语。
9. 控制设计范围：先复用已有模块，只为当前任务的实际调用方增加必要接口、状态或表。结构拆分先保持行为，再独立修改功能；不以文件行数/数量作目标，不把完整重构、全站美化或假设性的扩展能力作为样片和迁移的门槛。

## 三、统一数据流

```text
用户输入故事
  → 创建 Project（PostgreSQL）
  → 选择一种输入流程
     ├─ automatic：StoryDraft → 用户保存 → Script Split → Script Editor → Approval Gate
     └─ import：导入故事/剧本 → 规范化 → Script Split（必要时）→ Script Editor → Approval Gate
  → 已确认 Script
  → 下游 Storyboard / Visual / Audio / Composition / Export
```

模型消息必须先经过 Provider Adapter 归一化和契约校验，只有规范化后的 StoryDraft 或 Script 才能写入项目状态。浏览器不持有业务事实；刷新和 API 重启后都从 PostgreSQL 快照恢复。参考图只保存资产元数据和对象键，不参与本阶段文本生成。
