# 创建流程逆向审计与收敛方案

状态：待确认
日期：2026-09-05

## 审计结论

当前项目不需要重写，但创建入口需要收敛。现有实现同时承担三种意图：让 AI 扩写故事、让 AI 逐步问答、让用户把已有文本拆成剧本。三者在状态、接口和前端展示上互相交叉，是重复响应、模式串线、拆分失败和刷新恢复异常的主要来源。

建议把 MVP 收敛为两条明确路径：

1. **全自动生成**：用户输入一句话或故事，系统生成可编辑的完整故事文本；用户确认后再拆分为场景和镜头。
2. **用户剧本/故事拆分**：用户粘贴或上传自己的故事、剧本或结构化剧本，系统只负责解析、拆分、校验和进入后续生产。

逐步确认生成不作为当前 MVP 入口。它不是简单隐藏一个按钮，而是需要从产品状态、接口、Provider 契约、前端状态和测试中一起移除或隔离，否则旧状态仍会把请求导向 guided 分支。

## 现状证据

- `ProductionPipeline` 约 1700 行，同时处理项目创建、自动故事、逐步问答、剧本、角色、媒体、合成和导出。
- 创建页同时维护 `mode`、自动流式文本、guided transcript、草稿剧本、参考图和生成会话。
- 后端存在 `generate_story_text`、`generate_script`、`ask_guided_question`、`answer_guided_question`、`skip_guided_question`、`generate_detailed_script` 和 `advance_generation_session` 多组相互关联的入口。
- 当前测试虽然已覆盖大量接口，但正式 PostgreSQL/Redis/MinIO 集成仍有跳过项，说明本地 memory 通过不等于生产链路已完成。
- 现有 `MockTextProvider` 已能根据输入生成不同故事和多场景剧本，因此自动生成和剧本拆分的 Provider seam 可以保留。

## 根因分类

### 产品模型混杂

“生成故事”“生成完整剧本”“逐步问答”和“拆分用户文本”没有被定义为互斥的生产阶段。前端用多个布尔状态推断当前阶段，后端又用 `mode`、`stage`、`generationSession` 共同决定行为，导致同一项目可能被错误地发送到另一条路径。

### 状态事实重复

项目快照、浏览器本地状态、生成会话和 Redis 事件都携带部分阶段信息。刷新、重启或重复点击时，调用方无法只依赖一个权威状态判断下一步。

### 生成职责过宽

一个 `ProductionPipeline` 同时包含生成、编辑、资产、作业和导出逻辑。修改创建流程会触碰下游模块，导致局部修复产生回归。

### 输入契约不够集中

自动故事、剧本生成、剧本拆分和 guided 问答虽然共享 Provider，但各自有不同的归一化和状态处理。任何一个分支接受短文本、缺字段或旧格式，都会把错误推迟到编辑器或下游模块。

## 建议保留、删除和新增

### 保留

- 用户故事输入和项目创建。
- 全自动故事生成，包含流式进度、最小内容量、保存和重试。
- 用户自带故事/剧本导入。
- 故事到多场景多镜头剧本拆分。
- 剧本编辑、版本、校验和确认。
- 参考图上传和恢复。
- PostgreSQL 项目状态、Redis 事件/队列、Provider Adapter 和 Mock Provider。

### 当前删除或隔离

- 创建页逐步确认入口。
- `ask_guided_question`、`answer_guided_question`、`skip_guided_question` 和 `generate_detailed_script` 的产品调用链。
- guided transcript、question metadata、guided 自动推进和对应前端交互。

删除范围必须经过迁移期：先停止新项目创建 guided 状态，再处理旧项目的兼容读取，最后删除死代码和测试；不能直接删除方法后让历史项目 500。

### 新增

- 明确的入口类型：`generate_story`、`import_story`、`import_script`。
- 一个统一的 `parse_or_split_script` 生产阶段，输入可以是生成后的 StoryDraft 或用户文本。
- 一个权威的项目阶段枚举和阶段转换表。
- 导入前预览和校验：告诉用户识别出多少场景、镜头、对白和缺失字段，再允许保存。
- “使用我的剧本”入口，支持纯文本剧本；结构化 JSON 作为后续增强，不作为第一步前置条件。

## 推荐数据流

```text
入口选择
  ├─ 全自动：故事输入 → StoryDraft → 编辑保存
  ├─ 我的故事：用户文本 → StoryDraft 解析/校验 → 编辑保存
  └─ 我的剧本：用户文本 → Script 解析/拆分 → 预览修正
                       ↓
                Script Split/Normalize
                       ↓
                Script Editor → Confirmed Script
                       ↓
              Storyboard / Visual / Audio / Export
```

每个入口都写入同一个项目快照；浏览器只显示快照和事件，不保存阶段事实。Provider 只能返回规范化对象，不能直接写项目状态。

## 分阶段落地

### 阶段 A：入口收敛

验收：新项目只允许 `automatic`、`import_story`、`import_script`；旧 guided 项目仍能读取并显示迁移提示；后端拒绝不支持的新旧模式混用；删除 guided 新请求的 Playwright 覆盖。

### 阶段 B：自动路径稳定

验收：输入故事 → 流式生成至少 300/600/900 字符的结构化 StoryDraft → 保存 → 进入拆分；重复点击幂等；流式累计不重复；失败不污染项目快照。

### 阶段 C：用户文本/剧本拆分

验收：粘贴用户文本后可预览解析结果；至少生成 2/3/4 个场景和 6/8-10/10-12 个镜头；场景和镜头引用双向一致；缺字段显示逐项错误；用户可以修正后保存。

### 阶段 D：确认和下游 handoff

验收：确认只接受合法 Script；版本历史保留；确认后的 Script 能被现有 Storyboard 入口消费；创建阶段不修改画面、声音和导出实现。

### 阶段 E：清理 guided 死代码

验收：guided 新项目、接口、Provider 方法、前端状态和测试全部移除；旧数据有明确迁移策略；全量后端、前端和 Playwright 通过。

## 验收边界

本方案完成后，产品必须保证：

- 用户可以让系统帮忙生成故事，也可以完全使用自己的故事或剧本。
- 两条入口不会互相调用或共享错误的阶段状态。
- 任何进入剧本编辑器的结果都满足统一 Script Contract。
- 用户可以在确认前修正场景、镜头、对白、旁白和时长。
- 刷新、API 重启和重复请求不会丢失或重复生成项目状态。

本方案不承诺：自动理解参考图、重新设计下游生产模块、替换现有技术栈或一次性拆完所有后端大类。

## 决策请求

建议确认：是否接受“保留全自动 + 新增用户自有故事/剧本拆分 + 暂停并最终移除逐步确认生成”的 MVP 方向。确认后再创建对应 OpenSpec change 和逐项实施任务。

## 2026-09-05 创建入口布局回归

- 根因：创建页 `.mode-row` 仍使用两列网格，但入口已收敛为三个模式，第三项被隐式换行；入口没有稳定最小高度，窄视口下与后续控件产生视觉挤压。
- 决策：桌面明确使用三列 `minmax(0, 1fr)`，小屏明确使用单列；入口设置稳定最小高度、可收缩文本列和换行规则。
- 验收：390x844 视口下三个入口均至少 52px 高，按 DOM 边界顺序排列且无重叠；前端 typecheck/build 通过。
